# Спецификация Bidding Service

## 1. Назначение сервиса

**Bidding Service** — это сервис ставок для обработки рекламных запросов от новой DSP-площадки.

В текущей AS-IS архитектуре отдельного сервиса ставок нет. Логика выбора победителя находится внутри монолита 
в компоненте **Auction Engine**.

Эта логика выделяется в отдельный сервис, потому что она находится в критическом пути 
рекламного запроса и должна масштабироваться отдельно.

Основная задача Bidding Service:

* принять bid request от DSP через Gateway;
* подобрать подходящие кампании;
* рассчитать ставку;
* вернуть bid response;
* отправить технические события в Kafka.

---

## 2. Границы сервиса

Bidding Service отвечает только за быстрый расчёт ставки и формирование ответа для DSP.

### Входит в границы сервиса

Bidding Service отвечает за:

* обработку bid request;
* проверку обязательных полей запроса;
* подбор подходящих кампаний из Redis;
* применение правил таргетинга;
* проверку доступного бюджета по данным из Redis;
* расчёт ставки;
* формирование bid response или no-bid response;
* публикацию событий о результате обработки запроса в Kafka.

### Не входит в границы сервиса

Bidding Service не отвечает за:

* создание и изменение рекламных кампаний;
* хранение основной информации о кампаниях;
* пополнение бюджета;
* списание средств;
* построение отчётов;
* хранение кликов и показов;
* прямую работу с основной PostgreSQL.

Эти задачи относятся к другим сервисам: Campaign Service, Billing Service, Tracking Service и Analytics Service.

---

## 3. Основной сценарий работы

Основной поток обработки bid request:

```text
DSP
  -> DSP Gateway
  -> Bidding Service
  -> Redis
  -> Bidding Service
  -> DSP Gateway
  -> DSP
```

Bidding Service не должен обращаться к PostgreSQL во время обработки bid request.

Данные, которые нужны для быстрого расчёта ставки, заранее подготавливаются и хранятся в Redis.

---

## 4. API сервиса

### 4.1 Внутреннее API для Gateway

Gateway вызывает Bidding Service по внутреннему API.

Для этого взаимодействия предлагается использовать **gRPC**, потому что путь чувствителен к задержкам.

Пример метода:

```text
CalculateBid(BidRequest) returns (BidResponse)
```

### 4.2 BidRequest

Основные поля запроса:

| Поле           | Описание                                  |
| -------------- | ----------------------------------------- |
| `request_id`   | Уникальный идентификатор запроса          |
| `dsp_id`       | Идентификатор DSP-партнёра                |
| `user_id`      | Идентификатор пользователя, если доступен |
| `placement_id` | Место показа рекламы                      |
| `device_type`  | Тип устройства                            |
| `country`      | Страна пользователя                       |
| `page_url`     | URL страницы или приложения               |
| `floor_price`  | Минимальная цена показа                   |
| `timestamp`    | Время запроса                             |

### 4.3 BidResponse

Основные поля ответа:

| Поле          | Описание                               |
| ------------- | -------------------------------------- |
| `request_id`  | Идентификатор исходного запроса        |
| `status`      | `bid` или `no_bid`                     |
| `campaign_id` | Идентификатор выбранной кампании       |
| `creative_id` | Идентификатор креатива                 |
| `bid_price`   | Рассчитанная ставка                    |
| `ad_markup`   | Данные для показа рекламы              |
| `reason`      | Причина no-bid, если ставка не сделана |

Пример причин `no_bid`:

* нет подходящих кампаний;
* бюджет недоступен;
* ставка ниже минимальной цены;
* не прошёл таргетинг;
* временная ошибка зависимого компонента.

---

## 5. Зависимости сервиса

### 5.1 Redis

Redis используется как быстрое хранилище данных для аукциона.

Bidding Service читает из Redis:

* активные кампании;
* ставки;
* таргетинг;
* лимиты показов;
* доступные бюджеты;
* статусы кампаний.

Redis нужен, чтобы Bidding Service не ходил в PostgreSQL в критическом пути.

---

### 5.2 Campaign Service

Campaign Service отвечает за управление кампаниями.

Bidding Service не должен синхронно вызывать Campaign Service на каждый bid request.

Campaign Service публикует изменения кампаний в Kafka, после чего данные обновляются в Redis.

Так Bidding Service всегда работает с готовой быстрой моделью данных.

---

### 5.3 Billing Service

Billing Service отвечает за бюджеты, списания и финансовые операции.

Bidding Service использует только быстрые данные о доступном бюджете из Redis.

Финансовые списания не должны выполняться внутри Bidding Service. Они обрабатываются отдельно и должны быть 
идемпотентными.

---

### 5.4 Kafka

Kafka используется для событий.

Bidding Service может публиковать события:

* `bid.request.received`;
* `bid.response.sent`;
* `bid.no_bid`;
* `bid.error`.

События нужны для статистики, мониторинга и дальнейшей аналитики.

---

## 6. Модель данных

Bidding Service не является владельцем основной базы данных кампаний и финансов.

Его основная модель данных — это read-модель в Redis.

### 6.1 CampaignBidData

Данные кампании, нужные для расчёта ставки:

| Поле               | Описание               |
| ------------------ | ---------------------- |
| `campaign_id`      | Идентификатор кампании |
| `creative_id`      | Идентификатор креатива |
| `status`           | Статус кампании        |
| `base_bid`         | Базовая ставка         |
| `targeting_rules`  | Правила таргетинга     |
| `budget_available` | Доступный бюджет       |
| `daily_limit`      | Дневной лимит          |
| `priority`         | Приоритет кампании     |

### 6.2 BidDecision

Результат расчёта ставки:

| Поле          | Описание               |
| ------------- | ---------------------- |
| `request_id`  | Идентификатор запроса  |
| `campaign_id` | Выбранная кампания     |
| `creative_id` | Выбранный креатив      |
| `bid_price`   | Итоговая ставка        |
| `decision`    | `bid` или `no_bid`     |
| `reason`      | Причина решения        |
| `created_at`  | Время принятия решения |

BidDecision можно отправлять в Kafka, чтобы не записывать результат синхронно в базу данных.

---

## 7. Надёжность

### 7.1 Таймауты

Bidding Service должен иметь короткий таймаут обработки запроса.

Если сервис не успевает рассчитать ставку, лучше вернуть `no_bid`, чем задерживать ответ DSP.

---

### 7.2 Circuit Breaker

Для зависимостей нужно использовать Circuit Breaker.

Например, если Redis начал отвечать слишком медленно или часто ошибаться, сервис не должен зависать на каждом запросе.

В такой ситуации можно временно использовать резервную стратегию.

---

### 7.3 Резервная стратегия

Если данные недоступны, возможны два варианта:

* вернуть `no_bid`;
* использовать заранее подготовленные дефолтные данные, если это допустимо бизнес-правилами.

Для критичных ошибок безопаснее возвращать `no_bid`.

---

### 7.4 Повторные попытки

Повторные попытки не стоит делать в основном пути bid request, потому что они увеличивают время ответа.

Retry с экспоненциальной задержкой лучше использовать для фоновых операций:

* публикация событий;
* обновление кэша;
* обработка статистики;
* финансовые операции.

---

## 8. Наблюдаемость

Для Bidding Service нужно собирать метрики:

* количество bid request;
* количество bid response;
* количество no-bid ответов;
* время ответа;
* ошибки Redis;
* ошибки Kafka;
* долю таймаутов;
* P95 и P99 задержки.

Также нужно логировать `request_id`, чтобы можно было найти путь конкретного запроса.

---

## 9. Безопасность

Bidding Service не должен хранить секреты в коде или репозитории.

Ключи DSP, токены доступа, пароли Redis и Kafka должны храниться в переменных окружения или в отдельном хранилище секретов.

Входящие запросы должны проходить проверку на уровне DSP Gateway.
