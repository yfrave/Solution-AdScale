# DSP Gateway для интеграции с новой DSP

## 1. Назначение

**DSP Gateway** — это входной слой для новой DSP-площадки.

Он принимает внешние bid request, проверяет их, применяет ограничения и передаёт запросы во внутренний Bidding Service.

Gateway не должен содержать бизнес-логику расчёта ставки. Его задача — защитить Bidding Service
и обеспечить стабильную интеграцию с DSP.

Также Gateway отвечает за быструю проверку DSP-партнёра. Источником истины для DSP API keys 
и прав доступа является **Auth Service**, но Gateway не должен синхронно обращаться 
в Auth Service на каждый bid request, потому что это увеличит задержку в критическом пути.

---

## 2. Основной поток

```text
DSP
  -> DSP Gateway
  -> проверка DSP credentials по локальному кэшу Gateway
  -> Bidding Service
  -> DSP Gateway
  -> DSP
```

Описание:

1. DSP отправляет bid request.
2. DSP Gateway проверяет партнёра и формат запроса.
3. Gateway проверяет API key, HMAC-подпись или allowlist IP.
4. Gateway применяет rate limit и таймаут.
5. Gateway передаёт запрос в Bidding Service.
6. Bidding Service возвращает bid response или no-bid.
7. Gateway возвращает ответ обратно DSP.

Важно: в этом потоке нет синхронного вызова Auth Service на каждый bid request.

---

## 3. Роль Auth Service

**Auth Service** — это отдельный сервис авторизации и управления доступами.

Он отвечает за:

* хранение пользователей и ролей;
* авторизацию рекламодателей;
* выпуск и проверку JWT-токенов;
* хранение прав доступа;
* управление API keys для DSP-партнёров;
* управление сервисными credentials для внутренних интеграций.

У Auth Service должна быть своя база данных:

```text
auth_db
```

Для DSP-интеграции Auth Service является источником истины по ключам и правам доступа, 
но проверка в реальном RTB-потоке должна выполняться на стороне Gateway по локальному кэшу.

---

## 4. Обновление DSP credentials

Когда создаётся или изменяется DSP API key, данные обновляются через Auth Service.

Поток обновления:

```text
Администратор / Личный кабинет
  -> Gateway
  -> Auth Service
  -> auth_db
  -> Kafka
  -> обновление кэша DSP Gateway
```

Gateway хранит локальную read-модель разрешённых DSP-партнёров:

* `dsp_id`;
* статус DSP;
* hash API key;
* настройки HMAC;
* allowlist IP;
* лимиты RPS;
* доступные версии API.

Так Gateway может быстро проверять DSP без обращения в Auth Service на каждый запрос.

---

## 5. Внешний API

Для внешней интеграции используется:

```text
HTTPS / OpenRTB JSON
```

Основной маршрут:

```text
POST /openrtb/v1/bid
```

Назначение маршрута — принять bid request от DSP и вернуть bid response.

Пример заголовков:

| Заголовок                        | Назначение                                |
| -------------------------------- | ----------------------------------------- |
| `X-DSP-ID`                       | Идентификатор DSP-партнёра                |
| `X-Request-ID`                   | Идентификатор запроса                     |
| `Authorization`                  | API key, bearer token или подпись запроса |
| `X-Signature`                    | HMAC-подпись запроса, если используется   |
| `Content-Type: application/json` | Формат тела запроса                       |

---

## 6. Проверка DSP

Gateway должен проверять, что запрос пришёл от разрешённой DSP.

Возможные варианты проверки:

* API key;
* HMAC-подпись запроса;
* mTLS для более строгой интеграции;
* allowlist IP-адресов DSP.

Для учебного проекта можно выбрать вариант:

```text
API key + allowlist IP
```

Более надёжный вариант:

```text
API key + HMAC signature + allowlist IP
```

Проверка выполняется на Gateway по локальному кэшу credentials, который обновляется из Auth Service.

API keys нельзя хранить в коде или репозитории. Также не стоит хранить ключи в базе в открытом виде. 
Лучше хранить hash ключа или защищённое представление.

---

## 7. Ограничение частоты запросов

Gateway должен ограничивать частоту запросов от DSP.

Ограничения можно задавать:

* по `dsp_id`;
* по IP-адресу;
* по маршруту `/openrtb/v1/bid`;
* по версии API.

Пример:

```text
DSP-A: 5000 RPS
DSP-B: 2000 RPS
```

Лимиты для DSP можно хранить в Auth Service или отдельном Partner Registry, а Gateway будет получать их в локальный кэш.

Если лимит превышен, Gateway возвращает ошибку:

```text
HTTP 429 Too Many Requests
```

Это нужно, чтобы новая DSP не перегрузила Bidding Service.

---

## 8. Таймауты

Bid request должен обрабатываться быстро.

Gateway должен иметь короткие таймауты:

| Участок                                 | Таймаут          |
| --------------------------------------- | ---------------- |
| DSP -> Gateway                          | 80–100 ms        |
| Gateway -> Bidding Service              | 30–50 ms         |
| Проверка credentials по локальному кэшу | 1–3 ms           |
| Общий бюджет ответа                     | не больше 100 ms |

Если Bidding Service не успел ответить, Gateway возвращает `no-bid`.

Gateway не должен синхронно вызывать Auth Service в рамках bid request, потому что такой вызов может нарушить общий бюджет ответа.

---

## 9. Circuit Breaker

Для вызова Bidding Service нужно использовать Circuit Breaker.

Он нужен, чтобы Gateway не продолжал отправлять запросы в сервис, который уже массово ошибается или отвечает слишком медленно.

Пример логики:

* если растёт доля ошибок или таймаутов, Circuit Breaker открывается;
* новые запросы временно не отправляются в Bidding Service;
* Gateway сразу возвращает `no-bid`;
* через короткое время Gateway проверяет, восстановился ли сервис.

Это защищает систему от каскадной деградации.

Для Auth Service Circuit Breaker тоже нужен, но только для фонового обновления credentials. 
Если Auth Service временно недоступен, Gateway продолжает работать по последней валидной версии кэша.

---

## 10. Повторные попытки

Для основного bid request повторные попытки лучше не делать.

Причина: retry увеличивает время ответа, а у RTB-запросов жёсткое ограничение по задержке.

Повторные попытки можно использовать только для фоновых операций:

* обновление кэша DSP credentials из Auth Service;
* отправка технических событий;
* запись логов;
* обновление статистики;
* обработка финансовых событий.

Для таких операций retry должен быть с экспоненциальной задержкой.

Пример:

```text
1-я попытка: сразу
2-я попытка: через 1 секунду
3-я попытка: через 2 секунды
4-я попытка: через 4 секунды
```

---

## 11. Маршрутизация

Gateway маршрутизирует запросы по версии API и DSP-партнёру.

Пример маршрута:

```text
POST /openrtb/v1/bid -> Bidding Service
```

В будущем можно добавить новую версию:

```text
POST /openrtb/v2/bid -> Bidding Service v2
```

Это позволит менять внутреннюю реализацию без резкого отключения старой интеграции.

Для личного кабинета рекламодателя Gateway маршрутизирует запросы в другие сервисы:

```text
/api/v1/auth/*      -> Auth Service
/api/v1/campaigns/* -> Campaign Service
/api/v1/billing/*   -> Billing Service
/api/v1/reports/*   -> Analytics Service
```

---

## 12. Мониторинг

Gateway должен собирать метрики:

* количество запросов от DSP;
* количество успешных bid response;
* количество no-bid;
* количество ошибок;
* количество ответов `401`;
* количество ответов `403`;
* количество ответов `429`;
* время ответа Gateway;
* время ответа Bidding Service;
* P95 и P99 задержки;
* количество срабатываний Circuit Breaker;
* количество ошибок проверки credentials;
* возраст локального кэша DSP credentials;
* количество ошибок обновления кэша из Auth Service.

Также нужно логировать:

* `request_id`;
* `dsp_id`;
* статус ответа;
* время обработки;
* причину no-bid или ошибки;
* результат проверки credentials;
* `correlation_id`.

---

## 13. Ответы Gateway

Основные варианты ответа:

| Ситуация                            | Ответ                                |
| ----------------------------------- | ------------------------------------ |
| Ставка найдена                      | `200 OK` + bid response              |
| Нет подходящей ставки               | `204 No Content` или no-bid response |
| Неверный запрос                     | `400 Bad Request`                    |
| DSP не передала credentials         | `401 Unauthorized`                   |
| DSP передала невалидные credentials | `403 Forbidden`                      |
| DSP отключена или заблокирована     | `403 Forbidden`                      |
| Превышен лимит запросов             | `429 Too Many Requests`              |
| Bidding Service недоступен          | no-bid response                      |
| Внутренняя ошибка Gateway           | `500 Internal Server Error`          |

Для RTB-сценария при временных проблемах лучше возвращать no-bid, если это допустимо договорённостью с DSP.
