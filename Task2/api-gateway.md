# DSP Gateway для интеграции с новой DSP

## 1. Назначение

**DSP Gateway** — это входной слой для новой DSP-площадки.

Он принимает внешние bid request, проверяет их, применяет ограничения и передаёт запросы во внутренний Bidding Service.

Gateway не должен содержать бизнес-логику расчёта ставки. Его задача — защитить Bidding Service 
и обеспечить стабильную интеграцию с DSP.

---

## 2. Основной поток

```text
DSP
  -> DSP Gateway
  -> Bidding Service
  -> DSP Gateway
  -> DSP
```

Описание:

1. DSP отправляет bid request.
2. DSP Gateway проверяет партнёра и формат запроса.
3. Gateway применяет rate limit и таймаут.
4. Gateway передаёт запрос в Bidding Service.
5. Bidding Service возвращает bid response или no-bid.
6. Gateway возвращает ответ обратно DSP.

---

## 3. Внешний API

Для внешней интеграции используется:

```text
HTTPS / OpenRTB JSON
```

Основной маршрут:

```text
POST /openrtb/v1/bid
```

Назначение маршрута — принять bid request от DSP и вернуть bid response.

Пример заголовков:

| Заголовок                        | Назначение                 |
| -------------------------------- | -------------------------- |
| `X-DSP-ID`                       | Идентификатор DSP-партнёра |
| `X-Request-ID`                   | Идентификатор запроса      |
| `Authorization`                  | Токен или подпись запроса  |
| `Content-Type: application/json` | Формат тела запроса        |

---

## 4. Проверка DSP

Gateway должен проверять, что запрос пришёл от разрешённой DSP.

Возможные варианты проверки:

* API key;
* HMAC-подпись запроса;
* mTLS для более строгой интеграции;
* allowlist IP-адресов DSP.

---

## 5. Ограничение частоты запросов

Gateway должен ограничивать частоту запросов от DSP.

Ограничения можно задавать:

* по `dsp_id`;
* по IP-адресу;
* по маршруту `/openrtb/v1/bid`.

Пример:

```text
DSP-A: 5000 RPS
DSP-B: 2000 RPS
```

Если лимит превышен, Gateway возвращает ошибку:

```text
HTTP 429 Too Many Requests
```

Это нужно, чтобы новая DSP не перегрузила Bidding Service.

---

## 6. Таймауты

Bid request должен обрабатываться быстро.

Gateway должен иметь короткие таймауты:

| Участок                    | Таймаут          |
| -------------------------- | ---------------- |
| DSP -> Gateway             | 80–100 ms        |
| Gateway -> Bidding Service | 30–50 ms         |
| Общий бюджет ответа        | не больше 100 ms |

Если Bidding Service не успел ответить, Gateway возвращает `no-bid`.

---

## 7. Circuit Breaker

Для вызова Bidding Service нужно использовать Circuit Breaker.

Он нужен, чтобы Gateway не продолжал отправлять запросы в сервис, который уже массово ошибается или отвечает слишком медленно.

Пример логики:

* если растёт доля ошибок или таймаутов, Circuit Breaker открывается;
* новые запросы временно не отправляются в Bidding Service;
* Gateway сразу возвращает `no-bid`;
* через короткое время Gateway проверяет, восстановился ли сервис.

Это защищает систему от каскадной деградации.

---

## 8. Повторные попытки

Для основного bid request повторные попытки лучше не делать.

Причина: retry увеличивает время ответа, а у RTB-запросов жёсткое ограничение по задержке.

Повторные попытки можно использовать только для фоновых операций:

* отправка технических событий;
* запись логов;
* обновление статистики;
* обработка финансовых событий.

Для таких операций retry должен быть с экспоненциальной задержкой.

---

## 9. Маршрутизация

Gateway маршрутизирует запросы по версии API и DSP-партнёру.

Пример маршрута:

```text
POST /openrtb/v1/bid -> Bidding Service
```

В будущем можно добавить новую версию:

```text
POST /openrtb/v2/bid -> Bidding Service v2
```

Это позволит менять внутреннюю реализацию без резкого отключения старой интеграции.

---

## 10. Мониторинг

Gateway должен собирать метрики:

* количество запросов от DSP;
* количество успешных bid response;
* количество no-bid;
* количество ошибок;
* количество ответов `429`;
* время ответа Gateway;
* время ответа Bidding Service;
* P95 и P99 задержки;
* количество срабатываний Circuit Breaker.

Также нужно логировать:

* `request_id`;
* `dsp_id`;
* статус ответа;
* время обработки;
* причину no-bid или ошибки.

---

## 11. Ответы Gateway

Основные варианты ответа:

| Ситуация                   | Ответ                                  |
| -------------------------- | -------------------------------------- |
| Ставка найдена             | `200 OK` + bid response                |
| Нет подходящей ставки      | `204 No Content` или no-bid response   |
| Неверный запрос            | `400 Bad Request`                      |
| DSP не авторизована        | `401 Unauthorized` или `403 Forbidden` |
| Превышен лимит запросов    | `429 Too Many Requests`                |
| Bidding Service недоступен | no-bid response                        |
| Внутренняя ошибка Gateway  | `500 Internal Server Error`            |
