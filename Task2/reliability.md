# Надёжность RTB-интеграции

## 1. Задача

Нужно описать, как обеспечить надёжность новой RTB-интеграции с DSP.

Основной сценарий — обработка bid request:

```text
DSP
  -> DSP Gateway
  -> Bidding Service
  -> Redis
  -> Bidding Service
  -> DSP Gateway
  -> DSP
```

Этот путь критичен по времени. Ответ DSP должен возвращаться быстро, поэтому в основном потоке нельзя 
делать долгие операции, тяжёлые запросы в базу данных и бесконтрольные повторные попытки.

---

## 2. Основные принципы надёжности

Для RTB-интеграции используются следующие принципы:

* короткие таймауты;
* Circuit Breaker для зависимостей;
* отсутствие retry в критическом пути bid request;
* retry с exponential backoff для фоновых операций;
* fallback-стратегии при сбоях;
* идемпотентность финансовых операций;
* DLQ для событий, которые не удалось обработать;
* мониторинг ошибок, таймаутов и задержек.

Главная цель — не допустить каскадной деградации всей системы из-за сбоя одного компонента.

---

## 3. Таймауты

Bid request имеет жёсткое ограничение по времени.

Рекомендуемые таймауты:

| Участок                        |               Таймаут | Поведение при превышении                          |
| ------------------------------ | --------------------: | ------------------------------------------------- |
| DSP -> DSP Gateway             |             80–100 ms | Gateway возвращает no-bid или ошибку по контракту |
| DSP Gateway -> Bidding Service |              30–50 ms | Gateway возвращает no-bid                         |
| Bidding Service -> Redis       |               5–15 ms | Bidding Service использует fallback               |
| Публикация события в Kafka     | вне критического пути | Событие отправляется асинхронно                   |

Если сервис не успевает рассчитать ставку, лучше вернуть `no-bid`, чем задерживать ответ DSP.

---

## 4. Circuit Breaker

Circuit Breaker нужен, чтобы временно отключать зависимость, которая часто ошибается или отвечает слишком медленно.

### 4.1 Gateway -> Bidding Service

Если Bidding Service начал часто возвращать ошибки или таймауты, Circuit Breaker в Gateway открывается.

Поведение:

* новые запросы временно не отправляются в Bidding Service;
* Gateway сразу возвращает `no-bid`;
* через короткое время Gateway пропускает тестовые запросы;
* если Bidding Service восстановился, Circuit Breaker закрывается.

Это защищает Gateway и DSP от долгого ожидания.

---

### 4.2 Bidding Service -> Redis

Если Redis недоступен или отвечает слишком долго, Circuit Breaker открывается на стороне Bidding Service.

Поведение:

* Bidding Service не пытается обращаться к Redis на каждый запрос;
* используется fallback-стратегия;
* чаще всего возвращается `no-bid`;
* после восстановления Redis сервис снова начинает читать данные из кэша.

Для данных бюджета безопаснее вернуть `no-bid`, чем показать рекламу без актуальной информации о доступных средствах.

---

### 4.3 Bidding Service -> Kafka

Публикация событий в Kafka не должна задерживать ответ DSP.

Если Kafka временно недоступна:

* Bidding Service не должен блокировать ответ DSP;
* событие можно временно положить во внутренний буфер, если это безопасно;
* при невозможности отправки событие должно попасть в DLQ или технический лог;
* нужно поднять алерт.

События важны для статистики и аналитики, но они не должны ломать критический путь bid request.

---

## 5. Retry

### 5.1 Retry в критическом пути

В основном пути bid request retry не используется.

Причина:

* retry увеличивает время ответа;
* RTB-запросы чувствительны к задержкам;
* повторный вызов может не успеть уложиться в общий SLA;
* лучше быстро вернуть `no-bid`.

Это относится к вызовам:

```text
DSP Gateway -> Bidding Service
Bidding Service -> Redis
```

---

### 5.2 Retry для фоновых операций

Retry можно использовать для операций, которые не влияют на ответ DSP:

* публикация событий в Kafka;
* обработка событий консьюмерами;
* обновление Redis через Cache Updater;
* загрузка статистики в ClickHouse;
* финансовая обработка событий.

Для таких операций используется retry с exponential backoff.

Пример:

```text
1-я попытка: сразу
2-я попытка: через 1 секунду
3-я попытка: через 2 секунды
4-я попытка: через 4 секунды
5-я попытка: через 8 секунд
```

Желательно добавлять jitter, чтобы много сервисов не повторяли запрос одновременно.

---

## 6. DLQ

Если событие не удалось обработать после нескольких попыток, оно отправляется в DLQ.

Топик:

```text
dlq-events
```

DLQ нужен, чтобы одно проблемное событие не блокировало обработку всего потока.

В DLQ нужно сохранять:

* исходное событие;
* причину ошибки;
* количество попыток;
* время последней попытки;
* имя сервиса-обработчика;
* correlation_id.

После этого событие можно разобрать вручную или отдельным DLQ-обработчиком.

---

## 7. Fallback-стратегии

Fallback нужен, чтобы система могла корректно деградировать при сбоях.

| Сбой                        | Fallback                                                                     |
| --------------------------- | ---------------------------------------------------------------------------- |
| Bidding Service недоступен  | Gateway возвращает no-bid                                                    |
| Redis недоступен            | Bidding Service возвращает no-bid                                            |
| Нет данных по бюджету       | Bidding Service возвращает no-bid                                            |
| Нет подходящих кампаний     | Bidding Service возвращает no-bid                                            |
| Kafka недоступна            | Ответ DSP не блокируется, событие отправляется позже или попадает в DLQ      |
| ClickHouse недоступен       | Bid request продолжает работать, отчёты временно отстают                     |
| Campaign Service недоступен | Bidding Service продолжает работать по Redis read-модели                     |
| Billing Service недоступен  | Новые финансовые операции временно ограничиваются, бюджеты читаются из Redis |

Основной безопасный fallback для RTB — `no-bid`.

---

## 8. Использование устаревшего кэша

Для некоторых данных можно временно использовать устаревший кэш.

Пример:

* таргетинг;
* настройки DSP;
* список активных кампаний.

Но для финансово чувствительных данных нужно быть осторожнее.

Данные бюджета нельзя использовать слишком долго, потому что это может привести к показам без доступных средств.

Рекомендуемый подход:

| Данные          | Можно ли использовать устаревший кэш        |
| --------------- | ------------------------------------------- |
| Таргетинг       | Да, короткое время                          |
| Настройки DSP   | Да, короткое время                          |
| Ставки          | Да, если разрешено бизнес-правилами         |
| Бюджеты         | Только очень короткое время или no-bid      |
| Статус кампании | Лучше быстро обновлять, при сомнении no-bid |

---

## 9. Идемпотентность финансовых операций

Финансовые операции должны быть идемпотентными.

Это значит, что повторная обработка одного и того же события не должна приводить к повторному списанию денег.

Для этого используется уникальный идентификатор операции:

```text
operation_id
```

Пример:

```text
money.charged
operation_id = charge-123
```

Если Billing Service получил событие с таким `operation_id` повторно, он должен вернуть уже известный результат, 
а не выполнять списание ещё раз.

Для защиты можно использовать:

* уникальный индекс по `operation_id`;
* таблицу обработанных операций;
* проверку статуса операции перед списанием;
* транзакцию в PostgreSQL.

---

## 10. Надёжность Gateway

DSP Gateway защищает Bidding Service от нестабильного внешнего трафика.

Gateway должен выполнять:

* authentication;
* rate limiting;
* request validation;
* timeout control;
* Circuit Breaker;
* логирование request_id и dsp_id;
* сбор метрик по задержкам и ошибкам.

Если DSP отправляет слишком много запросов, Gateway возвращает:

```text
HTTP 429 Too Many Requests
```

Если запрос некорректный:

```text
HTTP 400 Bad Request
```

Если DSP не авторизована:

```text
HTTP 401 Unauthorized
```

или

```text
HTTP 403 Forbidden
```

---

## 11. Надёжность Kafka-потребителей

Kafka consumer должен быть идемпотентным.

Правила:

* offset фиксируется только после успешной обработки события;
* повторная доставка события не должна портить данные;
* при ошибке используется retry;
* после превышения лимита попыток событие отправляется в DLQ;
* ошибки обработки логируются с event_id и correlation_id.

Это важно для:

* обновления Redis;
* записи статистики в ClickHouse;
* финансовых операций.

---

## 12. Наблюдаемость

Для RTB-интеграции нужно собирать метрики:

* количество bid request;
* количество bid response;
* количество no-bid;
* P95 и P99 времени ответа;
* количество таймаутов;
* количество ошибок Gateway;
* количество ошибок Bidding Service;
* количество ошибок Redis;
* количество ошибок Kafka;
* количество срабатываний Circuit Breaker;
* consumer lag;
* количество событий в DLQ.

Также нужно логировать:

* `request_id`;
* `dsp_id`;
* `campaign_id`, если выбран;
* `correlation_id`;
* причину no-bid;
* причину ошибки;
* время обработки.

---

## 13. Безопасность

Секреты нельзя хранить в коде или репозитории.

Нельзя коммитить:

* DSP API keys;
* токены;
* пароли Redis;
* пароли Kafka;
* сертификаты;
* `.env` файлы;
* приватные ключи.

Секреты должны храниться в:

* переменных окружения;
* Kubernetes Secret;
* отдельном хранилище секретов.

Если секрет попал в Git, его нужно считать скомпрометированным и перевыпустить.
