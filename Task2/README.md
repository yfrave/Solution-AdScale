# Task2 — Проектирование RTB и интеграции с DSP

## Краткое описание

В рамках задачи проектируется архитектура RTB-компонента для интеграции AdScale с новой DSP-площадкой.

В текущей AS-IS архитектуре отдельного сервиса ставок нет. Логика выбора победителя рекламного аукциона находится 
внутри монолита в компоненте **Auction Engine**. В рамках этой задачи эта логика выделяется 
в отдельный **Bidding Service**.

Bidding Service должен быстро обрабатывать bid request от DSP, рассчитывать ставку и возвращать bid response. 
Это критичный сценарий, потому что ответ на рекламный запрос должен укладываться в жёсткое ограничение по времени.

Основная идея решения:

* внешняя DSP отправляет запросы через **DSP Gateway**;
* Gateway проверяет запрос, ограничивает частоту обращений и передаёт его в Bidding Service;
* Bidding Service рассчитывает ставку на основе данных из Redis;
* данные кампаний, ставок, таргетинга и бюджетов заранее подготавливаются из Campaign Service;
* события показов, кликов и результатов ставок отправляются в Kafka;
* финансовые операции обрабатываются отдельно и должны быть идемпотентными.

Для внешней интеграции с DSP используется **HTTPS / OpenRTB JSON**.

Для внутреннего критичного взаимодействия между Gateway и Bidding Service предлагается использовать **gRPC**, 
потому что этот путь чувствителен к задержкам.

Для событий показов и кликов используется **Kafka**, потому что эти события не должны замедлять ответ DSP 
и могут обрабатываться асинхронно.

В задаче также описаны паттерны надёжности:

* ограничение частоты запросов;
* таймауты;
* Circuit Breaker;
* повторные попытки с экспоненциальной задержкой для фоновых операций;
* идемпотентность финансовых операций;
* резервные стратегии при сбоях Redis или зависимых сервисов.
