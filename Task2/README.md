# Task2 — Проектирование RTB и интеграции с DSP

## Краткое описание

В рамках задачи проектируется архитектура RTB-компонента для интеграции AdScale с новой DSP-площадкой.

В текущей AS-IS архитектуре отдельного сервиса ставок нет. Логика выбора победителя рекламного аукциона находится 
внутри монолита в компоненте **Auction Engine**. В рамках этой задачи эта логика выделяется в отдельный **Bidding Service**.

Bidding Service должен быстро обрабатывать bid request от DSP, рассчитывать ставку и возвращать bid response. 
Это критичный сценарий, потому что ответ на рекламный запрос должен укладываться в жёсткое ограничение по времени.

Основная идея решения:

* внешняя DSP отправляет запросы через **DSP Gateway**;
* Gateway проверяет запрос, применяет rate limiting, контролирует таймауты и передаёт подготовленный запрос в Bidding Service;
* проверка DSP-партнёра выполняется на Gateway по быстрой read-модели credentials;
* Bidding Service рассчитывает ставку на основе данных из Redis;
* данные кампаний, ставок, таргетинга и бюджетов заранее подготавливаются из Campaign Service и Billing Service;
* события ставок, показов, кликов, кампаний, бюджетов и доступов отправляются в Kafka;
* финансовые операции обрабатываются отдельно и должны быть идемпотентными.

Для внешней интеграции с DSP используется **HTTPS / OpenRTB JSON**.

Для внутреннего критичного взаимодействия между Gateway и Bidding Service предлагается использовать **gRPC**, 
потому что этот путь чувствителен к задержкам.

Для событий используется **Kafka**, потому что события не должны замедлять ответ DSP и могут обрабатываться асинхронно.

Для быстрых данных аукциона используется **Redis**. Bidding Service не должен обращаться к PostgreSQL при обработке bid request.

Auth Service отвечает за пользователей, роли, JWT, refresh tokens и DSP credentials. Изменения доступов передаются через 
Kafka и обновляют кэш Gateway.

Целевые backend-сервисы и workers реализуются в едином стеке на **Go**. Инфраструктурные компоненты остаются отдельными
технологиями: API Gateway, Redis, Kafka, PostgreSQL и ClickHouse.

---

## Основной поток bid request

```text
DSP
  -> DSP Gateway
  -> Bidding Service
  -> Redis
  -> Bidding Service
  -> DSP Gateway
  -> DSP
```

В этом потоке нет синхронных обращений к PostgreSQL, Campaign Service, Billing Service или Analytics Service.

Gateway отвечает за внешний контур и защиту Bidding Service, а Bidding Service отвечает только за быстрый расчёт ставки.

---

## Обновление данных для аукциона

Данные для Bidding Service обновляются асинхронно.

Кампании и таргетинг:

```text
Campaign Service
  -> Kafka
  -> Cache Updater
  -> Redis
```

Бюджеты:

```text
Billing Service
  -> Kafka
  -> Cache Updater
  -> Redis
```

DSP credentials:

```text
Auth Service
  -> Kafka
  -> Auth Cache Updater
  -> Gateway credentials cache
```

Такой подход позволяет заранее подготовить данные для быстрого чтения и не замедлять RTB-запрос.

## Надёжность

В задаче описаны паттерны надёжности:

* ограничение частоты запросов;
* короткие таймауты;
* Circuit Breaker;
* отсутствие retry в критическом пути bid request;
* retry с exponential backoff для фоновых операций;
* DLQ для событий, которые не удалось обработать;
* идемпотентность финансовых операций;
* fallback-стратегии при сбоях Redis или зависимых сервисов;
* мониторинг P95/P99, ошибок, таймаутов, consumer lag и DLQ.

Основной безопасный fallback для RTB-сценария — `no-bid`.
