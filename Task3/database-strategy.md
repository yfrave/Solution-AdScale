# Стратегия данных AdScale

## 1. Задача

Нужно определить, какие хранилища данных использовать для сервисов AdScale после перехода к микросервисной архитектуре.

Главный принцип — **Database per Service**. Это значит, что каждый сервис должен владеть своими данными
и не должен напрямую читать таблицы другого сервиса.

Такой подход нужен, чтобы:

* убрать общую PostgreSQL как узкое место;
* разделить ответственность между сервисами;
* масштабировать разные части системы отдельно;
* снизить риск, что аналитика или статистика повлияют на рекламный аукцион;
* отделить авторизацию и управление доступами от бизнес-логики ставок, кампаний и финансов.

---

## 2. Выбор базы данных по сервисам

| Сервис                                            | Тип базы данных                          | Обоснование                                                                                                                                                         |
| ------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth Service / сервис авторизации                 | PostgreSQL `auth_db`                     | Хранит пользователей, роли, права доступа, refresh tokens и DSP API keys. Нужны транзакции, уникальность пользователей и надёжное хранение данных доступа.          |
| Bidding Service / сервис ставок                   | Redis как read-модель, Kafka для событий | Сервис находится в критическом пути bid request. Ему нельзя ходить в PostgreSQL при расчёте ставки. Он читает готовые данные из Redis и отправляет события в Kafka. |
| Campaign Service / сервис кампаний                | PostgreSQL `campaign_db`                 | Кампании, ставки и таргетинг — это рабочие бизнес-данные. Нужны транзакции, обновления и надёжное хранение.                                                         |
| Tracking / Statistics Service / сервис статистики | Kafka + ClickHouse                       | Поток показов, кликов и конверсий большой. Эти события лучше принимать через Kafka и записывать подготовленные данные в ClickHouse.                                 |
| Analytics Service / сервис аналитики              | ClickHouse                               | Аналитика выполняет тяжёлые отчёты и агрегации. ClickHouse лучше подходит для таких запросов, чем рабочая PostgreSQL.                                               |
| Billing Service / сервис финансов                 | PostgreSQL `billing_db`                  | Финансовым операциям нужны транзакции, строгая консистентность, история операций и защита от повторных списаний.                                                    |

## 3. Auth Service

Auth Service владеет базой `auth_db`.

Тип базы данных:

```text
PostgreSQL
```

Что хранится:

* пользователи рекламного кабинета;
* роли пользователей;
* права доступа;
* refresh tokens;
* DSP API keys;
* настройки DSP-партнёров;
* allowlist IP-адресов DSP;
* признаки блокировки или отключения партнёра.

Почему PostgreSQL:

* данные структурированные;
* нужны транзакции;
* нужна уникальность пользователей и ключей;
* важно хранить историю изменения доступов;
* нужно надёжно хранить данные авторизации.

Auth Service является источником истины для пользователей, ролей, JWT и DSP credentials.

При этом Auth Service не должен вызываться синхронно на каждый bid request.
Для RTB-сценария Gateway должен проверять DSP-партнёра по локальному кэшу credentials.

Поток обновления DSP credentials:

```text
Auth Service
  -> auth_db
  -> Kafka
  -> обновление кэша Gateway
```

Так Gateway может быстро проверять DSP API keys, HMAC-подпись и allowlist IP без задержки в критическом пути.

Важно: API keys, токены и секреты нельзя хранить в открытом виде. 
В базе лучше хранить hash ключа или защищённое представление.

---

## 4. Bidding Service

Bidding Service не владеет основной бизнес-базой данных.

Он использует Redis как быструю read-модель для данных, которые нужны при расчёте ставки:

* активные кампании;
* ставки;
* таргетинг;
* доступные бюджеты;
* лимиты показов;
* статусы кампаний.

Источник истины для этих данных находится в других сервисах:

* Campaign Service хранит кампании, ставки и таргетинг;
* Billing Service хранит балансы и финансовые операции.

Bidding Service получает уже подготовленную модель данных через Redis.

Это нужно, чтобы не обращаться к PostgreSQL в критическом пути рекламного запроса.

Проверка DSP-партнёра выполняется на уровне Gateway.

---

## 5. Campaign Service

Campaign Service владеет базой `campaign_db`.

Тип базы данных:

```text
PostgreSQL
```

Что хранится:

* рекламные кампании;
* ставки;
* правила таргетинга;
* статусы кампаний;
* креативы;
* лимиты кампаний.

Почему PostgreSQL:

* данные структурированные;
* нужны транзакции;
* есть операции создания, изменения и удаления;
* важно хранить историю изменений;
* данные кампаний являются источником истины для Redis.

После изменения кампании сервис публикует событие в Kafka. По этому событию обновляется Redis для Bidding Service.

---

## 6. Tracking / Statistics Service

Tracking / Statistics Service отвечает за поток событий:

* показы;
* клики;
* конверсии;
* результаты ставок.

Для этого используется:

```text
Kafka + ClickHouse
```

Kafka нужна для приёма и передачи большого потока событий.

ClickHouse нужен для хранения подготовленных данных статистики и дальнейшей аналитики.

Почему не PostgreSQL:

* событий может быть очень много;
* постоянная запись показов и кликов будет нагружать рабочую БД;
* отчёты по таким данным обычно требуют агрегаций;
* такие данные удобнее хранить в аналитическом хранилище.

---

## 7. Analytics Service

Analytics Service читает данные из ClickHouse.

Он не должен строить отчёты по рабочим PostgreSQL-базам Auth Service, Campaign Service или Billing Service.

Что хранится в ClickHouse:

* показы;
* клики;
* конверсии;
* расходы;
* агрегированные данные по кампаниям;
* данные по периодам.

Почему ClickHouse:

* хорошо подходит для аналитических запросов;
* быстро выполняет агрегации;
* позволяет хранить большие объёмы событий;
* отделяет отчёты от рабочих баз данных.

---

## 8. Billing Service

Billing Service владеет базой `billing_db`.

Тип базы данных:

```text
PostgreSQL
```

Что хранится:

* балансы рекламодателей;
* пополнения;
* списания;
* счета;
* история финансовых операций;
* идентификаторы операций для идемпотентности.

Почему PostgreSQL:

* финансовые данные требуют строгой консистентности;
* нужны транзакции;
* нельзя допускать двойных списаний;
* нужна история операций;
* важно иметь возможность расследовать спорные операции.

Для финансовых операций используется `operation_id`, чтобы повторная обработка одного события не привела
к повторному списанию.

---

## 9. Разделение ответственности

Каждый сервис должен обращаться только к своей базе данных.

Правило:

```text
Сервис не читает и не изменяет таблицы другого сервиса напрямую.
```

Примеры владения данными:

| Сервис                        | Своя зона ответственности                                   |
| ----------------------------- | ----------------------------------------------------------- |
| Auth Service                  | пользователи, роли, права, JWT/refresh tokens, DSP API keys |
| Campaign Service              | кампании, ставки, таргетинг, креативы                       |
| Billing Service               | балансы, платежи, списания, счета                           |
| Tracking / Statistics Service | события показов, кликов и конверсий                         |
| Analytics Service             | отчёты и аналитические данные                               |
| Bidding Service               | быстрый расчёт ставки на основе read-модели                 |

Если одному сервису нужны данные другого сервиса, используются:

* API;
* Kafka-события;
* read-модель в Redis;
* локальный кэш Gateway;
* аналитическая копия данных в ClickHouse.

Такой подход помогает избежать распределённого монолита.

## 10. Потоки обновления данных

### 10.1 Обновление кампаний

```text
Campaign Service
  -> campaign_db
  -> Kafka
  -> Cache Updater
  -> Redis
  -> Bidding Service
```

Campaign Service остаётся источником истины по кампаниям, а Redis используется только для быстрого чтения.

---

### 10.2 Обновление бюджетов

```text
Billing Service
  -> billing_db
  -> Kafka
  -> Cache Updater
  -> Redis
  -> Bidding Service
```

Billing Service остаётся источником истины по финансам, а Redis хранит только данные, нужные для быстрого аукциона.

---

### 10.3 Обновление DSP credentials

```text
Auth Service
  -> auth_db
  -> Kafka
  -> Gateway credentials cache
  -> DSP Gateway
```

Auth Service остаётся источником истины по DSP API keys и правам доступа, 
а Gateway использует локальный кэш для быстрой проверки DSP-запросов.

---

### 10.4 Обработка показов и кликов

```text
Tracking / Statistics Service
  -> Kafka
  -> Statistics Worker
  -> ClickHouse
  -> Analytics Service
```

Показы и клики не пишутся в рабочую PostgreSQL. Они обрабатываются асинхронно и попадают в ClickHouse для аналитики.

---

## 11. Хранилища данных

| Хранилище     | Владелец                                               | Что хранит                                                      |
| ------------- | ------------------------------------------------------ | --------------------------------------------------------------- |
| `auth_db`     | Auth Service                                           | пользователи, роли, права доступа, refresh tokens, DSP API keys |
| `campaign_db` | Campaign Service                                       | кампании, ставки, таргетинг, креативы                           |
| `billing_db`  | Billing Service                                        | балансы, списания, счета, финансовые операции                   |
| Redis         | Cache Updater / используется Bidding Service и Gateway | быстрые данные для аукциона и кэш DSP credentials               |
| Kafka         | инфраструктурный брокер событий                        | события ставок, показов, кликов, кампаний, бюджетов и доступов  |
| ClickHouse    | Analytics / Statistics контур                          | данные для аналитики и отчётов                                  |
