# Стратегия данных AdScale

## 1. Задача

Нужно определить, какие хранилища данных использовать для сервисов AdScale после перехода к микросервисной архитектуре.

Главный принцип — **Database per Service**. Это значит, что каждый сервис должен владеть своими данными 
и не должен напрямую читать таблицы другого сервиса.

Такой подход нужен, чтобы:

* убрать общую PostgreSQL как узкое место;
* разделить ответственность между сервисами;
* масштабировать разные части системы отдельно;
* снизить риск, что аналитика или статистика повлияют на рекламный аукцион.

---

## 2. Выбор базы данных по сервисам

| Сервис                                            | Тип базы данных                          | Обоснование                                                                                                                                                         |
| ------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bidding Service / сервис ставок                   | Redis как read-модель, Kafka для событий | Сервис находится в критическом пути bid request. Ему нельзя ходить в PostgreSQL при расчёте ставки. Он читает готовые данные из Redis и отправляет события в Kafka. |
| Campaign Service / сервис кампаний                | PostgreSQL                               | Кампании, ставки и таргетинг — это рабочие бизнес-данные. Нужны транзакции, обновления и надёжное хранение.                                                         |
| Tracking / Statistics Service / сервис статистики | Kafka + ClickHouse                       | Поток показов, кликов и конверсий большой. Эти события лучше принимать через Kafka и записывать подготовленные данные в ClickHouse.                                 |
| Analytics Service / сервис аналитики              | ClickHouse                               | Аналитика выполняет тяжёлые отчёты и агрегации. ClickHouse лучше подходит для таких запросов, чем рабочая PostgreSQL.                                               |
| Billing Service / сервис финансов                 | PostgreSQL                               | Финансовым операциям нужны транзакции, строгая консистентность, история операций и защита от повторных списаний.                                                    |

---

## 3. Bidding Service

Bidding Service не владеет основной бизнес-базой данных.

Он использует Redis как быструю read-модель для данных, которые нужны при расчёте ставки:

* активные кампании;
* ставки;
* таргетинг;
* доступные бюджеты;
* лимиты показов;
* статусы кампаний.

Источник истины для этих данных находится в других сервисах:

* Campaign Service хранит кампании, ставки и таргетинг;
* Billing Service хранит балансы и финансовые операции.

Bidding Service получает уже подготовленную модель данных через Redis.

Это нужно, чтобы не обращаться к PostgreSQL в критическом пути рекламного запроса.

---

## 4. Campaign Service

Campaign Service владеет базой `campaign_db`.

Тип базы данных:

```text
PostgreSQL
```

Что хранится:

* рекламные кампании;
* ставки;
* правила таргетинга;
* статусы кампаний;
* креативы;
* лимиты кампаний.

Почему PostgreSQL:

* данные структурированные;
* нужны транзакции;
* есть операции создания, изменения и удаления;
* важно хранить историю изменений;
* данные кампаний являются источником истины для Redis.

После изменения кампании сервис публикует событие в Kafka. По этому событию обновляется Redis для Bidding Service.

---

## 5. Tracking / Statistics Service

Tracking / Statistics Service отвечает за поток событий:

* показы;
* клики;
* конверсии;
* результаты ставок.

Для этого используется:

```text
Kafka + ClickHouse
```

Kafka нужна для приёма и передачи большого потока событий.

ClickHouse нужен для хранения подготовленных данных статистики и дальнейшей аналитики.

Почему не PostgreSQL:

* событий может быть очень много;
* постоянная запись показов и кликов будет нагружать рабочую БД;
* отчёты по таким данным обычно требуют агрегаций;
* такие данные удобнее хранить в аналитическом хранилище.

---

## 6. Analytics Service

Analytics Service читает данные из ClickHouse.

Он не должен строить отчёты по рабочим PostgreSQL-базам Campaign Service или Billing Service.

Что хранится в ClickHouse:

* показы;
* клики;
* конверсии;
* расходы;
* агрегированные данные по кампаниям;
* данные по периодам.

Почему ClickHouse:

* хорошо подходит для аналитических запросов;
* быстро выполняет агрегации;
* позволяет хранить большие объёмы событий;
* отделяет отчёты от рабочих баз данных.

---

## 7. Billing Service

Billing Service владеет базой `billing_db`.

Тип базы данных:

```text
PostgreSQL
```

Что хранится:

* балансы рекламодателей;
* пополнения;
* списания;
* счета;
* история финансовых операций;
* идентификаторы операций для идемпотентности.

Почему PostgreSQL:

* финансовые данные требуют строгой консистентности;
* нужны транзакции;
* нельзя допускать двойных списаний;
* нужна история операций;
* важно иметь возможность расследовать спорные операции.

Для финансовых операций используется `operation_id`, чтобы повторная обработка одного события не привела 
к повторному списанию.

---

## 8. Разделение ответственности

Каждый сервис должен обращаться только к своей базе данных.

Правило:

```text
Сервис не читает и не изменяет таблицы другого сервиса напрямую.
```

Если одному сервису нужны данные другого сервиса, используются:

* API;
* Kafka-события;
* read-модель в Redis;
* аналитическая копия данных в ClickHouse.

Такой подход помогает избежать распределённого монолита.
