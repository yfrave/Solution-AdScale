# Отказоустойчивость данных

## 1. Задача

Нужно описать, как в AdScale обеспечивается отказоустойчивость данных после перехода к микросервисной архитектуре.

Основные цели:

* не потерять критичные данные;
* быстро восстановить работу сервисов после сбоя;
* не допустить двойных финансовых операций;
* уметь восстановить данные из резервных копий;
* не хранить конфигурацию и секреты в коде.

---

## 2. RPO и RTO

**RPO** — сколько данных система может потерять при аварии.

**RTO** — за какое время систему нужно восстановить после аварии.

Для разных сервисов требования разные. Финансовые данные критичнее, чем временный кэш.

| Сервис                        | Хранилище                | RPO                                     | RTO         | Обоснование                                                                                               |
| ----------------------------- | ------------------------ | --------------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| Bidding Service               | Redis read-модель        | 0 для бизнес-данных, 1–5 минут для кэша | 5–10 минут  | Redis не является источником истины. Кэш можно восстановить из Campaign Service, Billing Service и Kafka. |
| Campaign Service              | PostgreSQL `campaign_db` | до 5 минут                              | 30–60 минут | Кампании важны для работы аукциона, но кратковременная задержка восстановления допустима.                 |
| Tracking / Statistics Service | Kafka + ClickHouse       | до 1–5 минут                            | 1–2 часа    | События должны сохраняться в Kafka. ClickHouse можно восстановить и догрузить события повторно.           |
| Analytics Service             | ClickHouse               | до 1 часа                               | 2–4 часа    | Аналитика важна, но не находится в критическом пути bid request.                                          |
| Billing Service               | PostgreSQL `billing_db`  | 0–1 минута                              | 15–30 минут | Финансовые операции критичны. Нельзя терять списания, платежи и историю операций.                         |

---

## 3. Campaign Service

Campaign Service хранит рабочие данные кампаний:

* кампании;
* ставки;
* таргетинг;
* креативы;
* статусы;
* лимиты.

Хранилище:

```text id="z97rds"
PostgreSQL campaign_db
```

### Отказоустойчивость

Для `campaign_db` используется:

* primary-replica репликация;
* автоматическое или полуавтоматическое переключение на реплику;
* регулярные резервные копии;
* восстановление на момент времени через WAL.

### Резервное копирование

Рекомендуемая стратегия:

* полный backup один раз в сутки;
* WAL-архивирование постоянно;
* проверка восстановления backup не реже одного раза в месяц;
* хранение backup в отдельном хранилище.

### Поведение при сбое

Если Campaign Service временно недоступен:

* существующие данные остаются в Redis;
* Bidding Service продолжает работать по текущей read-модели;
* новые изменения кампаний временно не принимаются;
* после восстановления события изменений снова обновляют Redis.

---

## 4. Billing Service

Billing Service хранит финансовые данные:

* балансы;
* платежи;
* списания;
* счета;
* историю операций;
* `operation_id` для идемпотентности.

Хранилище:

```text id="11tqqz"
PostgreSQL billing_db
```

### Отказоустойчивость

Для `billing_db` требования самые строгие.

Используется:

* primary-replica репликация;
* синхронная или почти синхронная репликация для критичных записей;
* WAL-архивирование;
* point-in-time recovery;
* контроль уникальности `operation_id`.

### Идемпотентность

Финансовые операции должны быть идемпотентными.

Пример:

```text id="qbatfv"
operation_id = уникальный идентификатор финансовой операции
```

Если одно событие придёт повторно, Billing Service должен понять, что операция уже обработана, и не списывать деньги второй раз.

### Резервное копирование

Рекомендуемая стратегия:

* полный backup один раз в сутки;
* WAL-архивирование постоянно;
* отдельное хранение backup;
* регулярная проверка восстановления;
* отдельные алерты на отставание реплики и ошибки backup.

---

## 5. Redis

Redis используется как read-модель для Bidding Service.

Он хранит:

* активные кампании;
* ставки;
* таргетинг;
* статусы;
* бюджеты;
* лимиты.

Redis не является источником истины.

### Отказоустойчивость

Для Redis используется:

```text id="r3imct"
Redis Cluster + replicas
```

Если один узел Redis недоступен, трафик переключается на реплику.

Если Redis полностью потерян, данные восстанавливаются через прогрев кэша:

```text id="4nh8gk"
Campaign Service / Billing Service
  -> Cache Warmer
  -> Redis
```

### RPO для Redis

Потеря Redis не считается потерей бизнес-данных, потому что данные можно восстановить из PostgreSQL и Kafka.

Но для стабильной работы bid request важно быстро восстановить read-модель.

### Поведение Bidding Service при сбое Redis

Если Redis не отвечает:

* применяется timeout;
* при частых ошибках срабатывает Circuit Breaker;
* Bidding Service возвращает `no-bid`;
* после восстановления Redis кэш прогревается заново.

---

## 6. Kafka

Kafka используется для событий:

* bid events;
* impression events;
* click events;
* campaign events;
* budget events;
* billing events.

### Отказоустойчивость

Для Kafka используется:

* несколько брокеров;
* replication factor не меньше 3;
* `min.insync.replicas = 2` для важных топиков;
* партиционирование топиков;
* consumer groups;
* DLQ для ошибочных событий.

### Поведение при сбое брокера

Если один брокер Kafka недоступен:

* партиции продолжают работать на других брокерах;
* producers и consumers переподключаются;
* consumer groups продолжают обработку после ребалансировки.

### DLQ

Если событие не удалось обработать после нескольких попыток, оно отправляется в:

```text id="3vykqd"
dlq-events
```

DLQ нужен, чтобы одно ошибочное событие не блокировало обработку всего потока.

---

## 7. ClickHouse

ClickHouse используется для аналитики и отчётов.

Он хранит:

* показы;
* клики;
* конверсии;
* результаты ставок;
* агрегированные данные;
* данные для отчётов.

### Отказоустойчивость

Для ClickHouse используется:

* репликация таблиц;
* партиционирование по дате;
* шардирование по `campaign_id` или `advertiser_id`;
* резервное копирование;
* возможность повторной загрузки данных из Kafka в пределах retention period.

### Резервное копирование

Рекомендуемая стратегия:

* backup ClickHouse один раз в сутки;
* хранение backup отдельно от основного кластера;
* проверка восстановления;
* возможность догрузить события из Kafka после восстановления.

Если ClickHouse временно недоступен, bid request продолжает работать, но отчёты могут быть временно недоступны или отставать.

---

## 8. Общая стратегия backup

| Хранилище                | Backup                      | Дополнительно                                            |
| ------------------------ | --------------------------- | -------------------------------------------------------- |
| PostgreSQL `campaign_db` | полный backup ежедневно     | WAL-архивирование, PITR                                  |
| PostgreSQL `billing_db`  | полный backup ежедневно     | WAL-архивирование, PITR, строгий контроль восстановления |
| Redis                    | backup не основной механизм | восстановление через cache warming                       |
| Kafka                    | репликация брокеров         | retention, DLQ, контроль consumer lag                    |
| ClickHouse               | backup ежедневно            | догрузка событий из Kafka                                |

Backup должен храниться отдельно от основного кластера.

Также нужно регулярно проверять восстановление, иначе backup нельзя считать рабочим.

---

## 9. Мониторинг отказоустойчивости

Нужно отслеживать:

* состояние PostgreSQL primary и replica;
* replication lag;
* успешность backup;
* возраст последнего backup;
* доступность Redis;
* Redis replication status;
* Kafka broker status;
* Kafka consumer lag;
* количество сообщений в DLQ;
* доступность ClickHouse;
* задержку записи событий в ClickHouse;
* ошибки восстановления кэша.

Для критичных метрик нужны алерты.

---

## 10. Соответствие 12-факторным приложениям

Архитектура должна соответствовать принципам 12-factor.

### Конфигурация вне кода

Пароли, токены, адреса PostgreSQL, Redis, Kafka и ClickHouse нельзя хранить в репозитории.

Их нужно передавать через:

* переменные окружения;
* Kubernetes Secret;
* отдельное хранилище секретов.

### Зависимости явно описаны

Каждый сервис должен иметь явно описанные зависимости:

* база данных;
* Kafka;
* Redis;
* ClickHouse;
* внешние API.

### Stateless-сервисы

Приложения должны быть stateless.

Состояние хранится в базах данных, Redis или Kafka, а не внутри процесса приложения.

Это позволяет горизонтально масштабировать сервисы.

### Логи как поток событий

Сервисы должны писать логи в stdout/stderr.

Дальше их собирает инфраструктура логирования.

### Быстрый запуск и остановка

Сервисы должны корректно обрабатывать shutdown:

* завершить текущие запросы;
* остановить consumer;
* зафиксировать offset после успешной обработки события;
* не потерять сообщение в середине обработки.

### Одинаковый код для окружений

Один и тот же код должен использоваться для dev, test и prod.

Различаться должны только конфигурация и инфраструктурные параметры.

---

## 11. Безопасность

Нельзя хранить в Git:

* пароли PostgreSQL;
* пароли Redis;
* Kafka credentials;
* сертификаты;
* токены DSP;
* приватные ключи;
* `.env` файлы.

Для этого в `.gitignore` должны быть добавлены:

```text id="4spz58"
.env
.env.*
*.key
*.pem
*.p12
*.jks
```

Если секрет случайно попал в репозиторий, его нужно считать скомпрометированным и перевыпустить.

---

## 12. Итог

В AdScale отказоустойчивость строится по-разному для разных типов данных.

Главные решения:

* PostgreSQL для Campaign и Billing работает с репликацией и backup;
* Billing Service имеет самые строгие RPO/RTO;
* Redis можно восстановить через прогрев кэша;
* Kafka использует репликацию, retention и DLQ;
* ClickHouse можно восстановить из backup и догрузить события из Kafka;
* все сервисы должны быть stateless и хранить конфигурацию вне кода.
