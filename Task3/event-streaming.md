# Архитектура потоковой обработки событий

## 1. Задача

Нужно описать, как в AdScale будет организована потоковая обработка событий.

Kafka используется для событий, которые не должны замедлять основной рекламный запрос:

* bid request / bid response;
* показы;
* клики;
* конверсии;
* изменения кампаний;
* изменения бюджетов;
* финансовые события.

Главная цель — не писать большой поток событий напрямую в PostgreSQL и не мешать работе Bidding Service.

---

## 2. Почему Kafka

Kafka подходит для AdScale, потому что:

* событий показов и кликов может быть много;
* события можно обрабатывать асинхронно;
* разные потребители могут читать одни и те же события независимо;
* события можно хранить некоторое время и перечитывать при необходимости;
* Kafka помогает сглаживать пики нагрузки.

Kafka не используется для синхронного ответа DSP. Ответ DSP должен возвращаться быстро, а события можно обработать позже.

---

## 3. Основные топики

| Топик               | Что хранит                                | Ключ партиционирования    |
| ------------------- | ----------------------------------------- | ------------------------- |
| `bid-events`        | события ставок и no-bid                   | `request_id` или `dsp_id` |
| `impression-events` | показы рекламы                            | `campaign_id`             |
| `click-events`      | клики по рекламе                          | `campaign_id`             |
| `conversion-events` | конверсии                                 | `campaign_id`             |
| `campaign-events`   | изменения кампаний, ставок и таргетинга   | `campaign_id`             |
| `budget-events`     | изменения бюджетов                        | `advertiser_id`           |
| `billing-events`    | списания, пополнения, финансовые операции | `operation_id`            |
| `dlq-events`        | события, которые не удалось обработать    | исходный ключ события     |

---

## 4. Формат событий

Предлагается формат:

```text
JSON Schema
```

Почему JSON Schema:

* проще читать и проверять;
* удобно использовать в документации;
* подходит для интеграции между сервисами;
* легче отлаживать, чем бинарные форматы.

Avro тоже можно использовать, особенно при высокой нагрузке и строгом контроле схем, 
но для этой задачи JSON Schema достаточно.

---

## 5. Общие поля события

У всех событий должны быть общие технические поля:

| Поле             | Описание                         |
| ---------------- | -------------------------------- |
| `event_id`       | уникальный идентификатор события |
| `event_type`     | тип события                      |
| `event_version`  | версия схемы события             |
| `occurred_at`    | время возникновения события      |
| `producer`       | сервис, который создал событие   |
| `correlation_id` | идентификатор цепочки запроса    |
| `payload`        | бизнес-данные события            |

Пример:

```json
{
  "event_id": "evt-123",
  "event_type": "impression.created",
  "event_version": 1,
  "occurred_at": "2026-06-18T12:00:00Z",
  "producer": "tracking-service",
  "correlation_id": "req-456",
  "payload": {
    "campaign_id": "cmp-10",
    "advertiser_id": "adv-20",
    "placement_id": "main-page-top",
    "price": 1.25
  }
}
```

---

## 6. События ставок

Топик:

```text
bid-events
```

Примеры событий:

* `bid.request.received`;
* `bid.response.sent`;
* `bid.no_bid`;
* `bid.error`.

Эти события нужны для мониторинга RTB-процесса и последующей аналитики.

Bidding Service публикует события асинхронно. Если публикация события временно не удалась, 
она не должна задерживать ответ DSP.

---

## 7. События показов, кликов и конверсий

Топики:

```text
impression-events
click-events
conversion-events
```

Эти события создаёт Tracking / Statistics Service.

Дальше их читают обработчики статистики и записывают подготовленные данные в ClickHouse.

Основной поток:

```text
Tracking / Statistics Service
  -> Kafka
  -> Statistics Worker
  -> ClickHouse
```

Так показы и клики не пишутся напрямую в PostgreSQL и не мешают рекламному аукциону.

---

## 8. События кампаний

Топик:

```text
campaign-events
```

Примеры событий:

* `campaign.created`;
* `campaign.updated`;
* `campaign.paused`;
* `campaign.deleted`;
* `bid.changed`;
* `targeting.changed`.

Эти события публикует Campaign Service.

Их читает Cache Updater и обновляет Redis.

Поток:

```text
Campaign Service
  -> Kafka
  -> Cache Updater
  -> Redis
```

Так Bidding Service получает актуальные данные из Redis и не вызывает Campaign Service при каждом bid request.

---

## 9. События бюджетов и финансов

Топики:

```text
budget-events
billing-events
```

Примеры событий:

* `budget.changed`;
* `payment.completed`;
* `payment.failed`;
* `money.charged`;
* `invoice.created`.

Эти события публикует Billing Service.

Для финансовых событий важна идемпотентность. В каждом событии должен быть уникальный `operation_id`, 
чтобы повторная обработка не привела к повторному списанию.

---

## 10. Группы потребителей

| Consumer group            | Что читает                                                             | Что делает                              |
| ------------------------- | ---------------------------------------------------------------------- | --------------------------------------- |
| `cache-updater-group`     | `campaign-events`, `budget-events`                                     | обновляет Redis                         |
| `statistics-worker-group` | `bid-events`, `impression-events`, `click-events`, `conversion-events` | готовит статистику и пишет в ClickHouse |
| `billing-worker-group`    | `impression-events`, `click-events`, `billing-events`                  | обрабатывает финансовые события         |
| `analytics-loader-group`  | события статистики                                                     | загружает данные для отчётов            |
| `monitoring-group`        | основные события                                                       | считает технические метрики             |
| `dlq-handler-group`       | `dlq-events`                                                           | разбирает ошибочные события             |

Каждая группа потребителей может масштабироваться отдельно.

---

## 11. Политика хранения

Рекомендуемая политика хранения:

| Топик               | Retention                      |
| ------------------- | ------------------------------ |
| `bid-events`        | 7 дней                         |
| `impression-events` | 14–30 дней                     |
| `click-events`      | 14–30 дней                     |
| `conversion-events` | 30 дней                        |
| `campaign-events`   | 30–90 дней                     |
| `budget-events`     | 30–90 дней                     |
| `billing-events`    | 90 дней или больше             |
| `dlq-events`        | до ручного разбора или 30 дней |

Для финансовых событий срок хранения должен быть больше, потому что они могут понадобиться для сверки 
и расследования спорных операций.

---

## 12. Обработка ошибок

Если обработчик не смог обработать событие, применяется такая логика:

1. Повторить обработку несколько раз.
2. Использовать экспоненциальную задержку между попытками.
3. Если событие всё равно не обработано, отправить его в `dlq-events`.
4. Сохранить причину ошибки.
5. Разобрать событие вручную или отдельным обработчиком DLQ.

DLQ нужен, чтобы проблемные события не блокировали обработку всего потока.

---

## 13. Идемпотентность потребителей

Kafka может доставить событие повторно, поэтому потребители должны быть идемпотентными.

Это значит, что повторная обработка одного события не должна портить данные.

Для этого используются:

* `event_id`;
* `operation_id` для финансовых операций;
* таблица или хранилище обработанных событий;
* уникальные ограничения на стороне базы;
* проверка версии события.

Особенно важно это для Billing Service, потому что повторная обработка финансового события может привести 
к двойному списанию.

---

## 14. Мониторинг Kafka

Нужно отслеживать:

* количество сообщений в топиках;
* consumer lag;
* количество ошибок обработки;
* количество событий в DLQ;
* скорость записи и чтения;
* задержку доставки событий;
* доступность брокеров Kafka.

Для критичных топиков нужно настроить алерты.

---

## 15. Безопасность

Доступ к Kafka должен быть ограничен.

Нужно защитить:

* адреса брокеров;
* логины и пароли;
* сертификаты;
* ключи доступа;
* настройки подключения.

Эти данные нельзя хранить в коде или репозитории. Их нужно передавать через переменные окружения или хранилище секретов.

---

## 16. Итог

Kafka используется как основа для асинхронной обработки событий в AdScale.

Основные решения:

* bid, impression, click и conversion события передаются через Kafka;
* изменения кампаний и бюджетов обновляют Redis через Cache Updater;
* события статистики записываются в ClickHouse;
* финансовые события обрабатываются идемпотентно;
* ошибки отправляются в DLQ;
* потребители масштабируются через consumer groups.

Такой подход снижает нагрузку на PostgreSQL и позволяет обрабатывать большой поток событий без замедления bid request.
