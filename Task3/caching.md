# Дизайн кэширования

## 1. Задача

Нужно описать, как использовать кэширование в AdScale после выделения сервисов.

Главная цель кэша — ускорить обработку bid request и убрать PostgreSQL из критического пути рекламного аукциона.

Bidding Service должен получать нужные данные из Redis, а не читать их из PostgreSQL при каждом запросе.

---

## 2. Что кэшировать

В Redis нужно хранить данные, которые часто читаются при расчёте ставки:

| Данные            | Зачем нужны                                             |
| ----------------- | ------------------------------------------------------- |
| Активные кампании | Чтобы быстро найти кандидатов для показа                |
| Ставки            | Чтобы рассчитать bid price                              |
| Таргетинг         | Чтобы проверить, подходит ли кампания под запрос        |
| Статусы кампаний  | Чтобы не участвовать в аукционе с выключенной кампанией |
| Доступные бюджеты | Чтобы не показывать рекламу без бюджета                 |
| Лимиты показов    | Чтобы не превышать дневные или общие ограничения        |
| Данные DSP        | Чтобы применять настройки конкретного партнёра          |

---

## 3. Где размещается Redis

Redis размещается рядом с Bidding Service, потому что именно этот сервис сильнее всего зависит от скорости чтения.

Рекомендуемый вариант:

```text
Bidding Service
  -> Redis Cluster
```

Redis должен быть развёрнут как кластер с репликами.

Это нужно, чтобы:

* распределить нагрузку;
* снизить задержку чтения;
* переживать отказ отдельного узла;
* масштабировать кэш при росте нагрузки.

---

## 4. Источники данных для Redis

Redis не является источником истины.

Источники истины:

| Данные                      | Источник истины                  |
| --------------------------- | -------------------------------- |
| Кампании, ставки, таргетинг | Campaign Service / `campaign_db` |
| Бюджеты и балансы           | Billing Service / `billing_db`   |
| События изменений           | Kafka                            |

Redis хранит только подготовленную read-модель для быстрого чтения.

---

## 5. Обновление кэша

Обновление Redis происходит через события.

Основной поток:

```text
Campaign Service / Billing Service
  -> Kafka
  -> Cache Updater
  -> Redis
  -> Bidding Service
```

Примеры событий:

* `campaign.created`;
* `campaign.updated`;
* `campaign.paused`;
* `campaign.deleted`;
* `bid.changed`;
* `budget.changed`;
* `daily_limit.changed`.

Так Bidding Service получает актуальные данные без синхронных вызовов в Campaign Service или Billing Service.

---

## 6. TTL

TTL нужен, чтобы данные в Redis не жили бесконечно и постепенно обновлялись.

Рекомендуемые значения:

| Данные            | TTL          |
| ----------------- | ------------ |
| Активные кампании | 1–5 минут    |
| Ставки            | 1–5 минут    |
| Таргетинг         | 5–15 минут   |
| Статусы кампаний  | 30–60 секунд |
| Доступные бюджеты | 5–15 секунд  |
| Лимиты показов    | 30–60 секунд |
| Настройки DSP     | 5–15 минут   |

Для бюджетов TTL должен быть короче, потому что эти данные чаще меняются и влияют на корректность показа рекламы.

---

## 7. Инвалидация кэша

Используются три способа инвалидации.

### 7.1 По событию

Основной способ.

Когда Campaign Service или Billing Service меняет данные, он публикует событие в Kafka. 
Cache Updater читает событие и обновляет Redis.

Пример:

```text
campaign.updated
  -> Cache Updater
  -> обновить campaign:{campaign_id}
```

### 7.2 По TTL

Если событие не пришло или обработалось с задержкой, запись всё равно обновится после истечения TTL.

TTL используется как страховка от устаревших данных.

### 7.3 По версии

Для важных данных можно хранить версию.

Пример:

```text
campaign:{campaign_id}:version
```

Если версия в событии новее версии в Redis, Cache Updater обновляет запись.

Это помогает не применить старое событие поверх нового состояния.

---

## 8. Прогрев кэша

Прогрев кэша нужен, чтобы Bidding Service не начал работу с пустым Redis.

Кэш нужно прогревать:

* при старте системы;
* после перезапуска Redis;
* перед ожидаемыми пиковыми нагрузками;
* после массового обновления кампаний.

Основной поток прогрева:

```text
Cache Warmer
  -> Campaign Service
  -> Billing Service
  -> Redis
```

Что загружается при прогреве:

* активные кампании;
* ставки;
* таргетинг;
* статусы кампаний;
* доступные бюджеты.

Важно: прогрев кэша не должен перегружать PostgreSQL. Поэтому данные нужно загружать пакетами и с ограничением скорости.

---

## 9. Поведение при сбоях Redis

Если Redis недоступен, Bidding Service не должен зависать.

Возможные действия:

| Ситуация                         | Действие                                                   |
| -------------------------------- | ---------------------------------------------------------- |
| Redis отвечает медленно          | Сработает timeout                                          |
| Redis часто ошибается            | Сработает Circuit Breaker                                  |
| Нет данных по кампании           | Вернуть no-bid                                             |
| Нет данных по бюджету            | Вернуть no-bid                                             |
| Есть безопасные дефолтные данные | Использовать fallback, если это разрешено бизнес-правилами |

Для финансово чувствительных данных безопаснее вернуть `no-bid`, чем показать рекламу без актуального бюджета.

---

## 10. Ключи Redis

Пример структуры ключей:

```text
campaign:{campaign_id}
campaign:{campaign_id}:targeting
campaign:{campaign_id}:bid
campaign:{campaign_id}:status
budget:{advertiser_id}
limit:{campaign_id}:daily
dsp:{dsp_id}:settings
```

Для списков активных кампаний можно использовать ключи:

```text
active_campaigns:{placement_id}
active_campaigns:{country}
active_campaigns:{device_type}
```

Так Bidding Service сможет быстрее находить подходящие кампании для конкретного bid request.

---

## 11. Метрики кэша

Для Redis и Cache Updater нужно собирать метрики:

* hit rate;
* miss rate;
* время ответа Redis;
* количество ошибок Redis;
* количество истёкших ключей;
* задержка обновления кэша после события;
* количество событий, которые не удалось обработать;
* размер кэша;
* количество срабатываний Circuit Breaker.

Эти метрики нужны, чтобы понимать, насколько кэш помогает и не устарели ли данные.

---

## 12. Безопасность

Пароли Redis и параметры подключения нельзя хранить в коде или репозитории.

Их нужно хранить:

* в переменных окружения;
* в Kubernetes Secret;
* в отдельном хранилище секретов.

Доступ к Redis должен быть только у сервисов, которым он действительно нужен:

* Bidding Service;
* Cache Updater;
* Cache Warmer;
* сервисы мониторинга.
