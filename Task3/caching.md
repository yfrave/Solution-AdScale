# Дизайн кэширования

## 1. Задача

Нужно описать, как использовать кэширование в AdScale после выделения сервисов.

Главная цель кэша — ускорить обработку bid request и убрать PostgreSQL из критического пути рекламного аукциона.

Bidding Service должен получать данные для расчёта ставки из Redis, а не читать их из PostgreSQL при каждом запросе.

Также в архитектуре используется отдельный кэш на стороне Gateway для быстрой проверки DSP-партнёров.

---

## 2. Что кэшировать

В Redis нужно хранить данные, которые часто читаются при расчёте ставки:

| Данные            | Зачем нужны                                             |
| ----------------- | ------------------------------------------------------- |
| Активные кампании | Чтобы быстро найти кандидатов для показа                |
| Ставки            | Чтобы рассчитать bid price                              |
| Таргетинг         | Чтобы проверить, подходит ли кампания под запрос        |
| Статусы кампаний  | Чтобы не участвовать в аукционе с выключенной кампанией |
| Доступные бюджеты | Чтобы не показывать рекламу без бюджета                 |
| Лимиты показов    | Чтобы не превышать дневные или общие ограничения        |
| Настройки DSP     | Чтобы применять настройки конкретного партнёра          |

Отдельно от Redis для аукциона используется **Gateway credentials cache**.

Он хранит данные, которые нужны Gateway для проверки DSP:

| Данные             | Зачем нужны                                               |
| ------------------ | --------------------------------------------------------- |
| `dsp_id`           | Идентификатор DSP-партнёра                                |
| статус DSP         | Чтобы отключённый партнёр не мог отправлять bid request   |
| `key_id`           | Идентификатор ключа                                       |
| hash ключа         | Для проверки API key без хранения секрета в открытом виде |
| allowlist IP       | Для ограничения источников запросов                       |
| RPS-лимиты         | Для rate limiting                                         |
| версия credentials | Чтобы не применить старое событие поверх нового           |

---

## 3. Где размещается кэш

Для данных аукциона используется Redis рядом с Bidding Service:

```text
Bidding Service
  -> Redis Cluster
```

Redis должен быть развёрнут как кластер с репликами.

Это нужно, чтобы:

* распределить нагрузку;
* снизить задержку чтения;
* переживать отказ отдельного узла;
* масштабировать кэш при росте нагрузки.

Для проверки DSP используется отдельный кэш на стороне Gateway:

```text
DSP Gateway
  -> Gateway credentials cache
```

Этот кэш может быть in-memory или Redis-backed. Главное требование — очень быстрое чтение в момент обработки внешнего bid request.

---

## 4. Источники данных для кэша

Redis и Gateway credentials cache не являются источниками истины.

Источники истины:

| Данные                          | Источник истины                  |
| ------------------------------- | -------------------------------- |
| Кампании, ставки, таргетинг     | Campaign Service / `campaign_db` |
| Бюджеты и балансы               | Billing Service / `billing_db`   |
| DSP credentials и права доступа | Auth Service / `auth_db`         |
| События изменений               | Kafka                            |

Кэши хранят только подготовленные read-модели для быстрого чтения.

---

## 5. Обновление кэша

Обновление кэша происходит через события.

Для данных аукциона:

```text
Campaign Service / Billing Service
  -> Kafka
  -> Cache Updater
  -> Redis
  -> Bidding Service
```

Примеры событий:

* `campaign.created`;
* `campaign.updated`;
* `campaign.paused`;
* `campaign.deleted`;
* `bid.changed`;
* `budget.changed`;
* `daily_limit.changed`.

Для данных доступа:

```text
Auth Service
  -> Kafka
  -> Auth Cache Updater
  -> Gateway credentials cache
  -> DSP Gateway
```

Примеры событий:

* `dsp_partner.created`;
* `dsp_partner.blocked`;
* `auth.credentials.changed`;
* `api_key.rotated`;
* `access.changed`.

Так Bidding Service получает данные для аукциона из Redis, а Gateway получает данные для проверки DSP из своего кэша.

---

## 6. TTL

TTL нужен, чтобы данные в кэше не жили бесконечно и постепенно обновлялись.

Рекомендуемые значения:

| Данные            | TTL          |
| ----------------- | ------------ |
| Активные кампании | 1–5 минут    |
| Ставки            | 1–5 минут    |
| Таргетинг         | 5–15 минут   |
| Статусы кампаний  | 30–60 секунд |
| Доступные бюджеты | 5–15 секунд  |
| Лимиты показов    | 30–60 секунд |
| Настройки DSP     | 5–15 минут   |
| DSP credentials   | 1–5 минут    |

Для бюджетов TTL должен быть короче, потому что эти данные чаще меняются и влияют на корректность показа рекламы.

Для credentials TTL тоже должен быть ограниченным, чтобы блокировка или ротация ключей применялась достаточно быстро.

---

## 7. Инвалидация кэша

Используются три способа инвалидации.

### 7.1 По событию

Основной способ.

Когда сервис-владелец меняет данные, он публикует событие в Kafka. Обработчик читает событие и обновляет нужный кэш.

Пример для кампании:

```text
campaign.updated
  -> Cache Updater
  -> обновить campaign:{campaign_id}
```

Пример для DSP credentials:

```text
auth.credentials.changed
  -> Auth Cache Updater
  -> обновить dsp:{dsp_id}:credentials
```

---

### 7.2 По TTL

Если событие не пришло или обработалось с задержкой, запись всё равно обновится после истечения TTL.

TTL используется как страховка от устаревших данных.

---

### 7.3 По версии

Для важных данных можно хранить версию.

Пример:

```text
campaign:{campaign_id}:version
dsp:{dsp_id}:credentials:version
```

Если версия в событии новее версии в кэше, обработчик обновляет запись.

Это помогает не применить старое событие поверх нового состояния.

---

## 8. Прогрев кэша

Прогрев кэша нужен, чтобы Bidding Service не начал работу с пустым Redis.

Кэш нужно прогревать:

* при старте системы;
* после перезапуска Redis;
* перед ожидаемыми пиковыми нагрузками;
* после массового обновления кампаний.

Основной поток прогрева Redis:

```text
Cache Warmer
  -> Campaign Service
  -> Billing Service
  -> Redis
```

Что загружается при прогреве:

* активные кампании;
* ставки;
* таргетинг;
* статусы кампаний;
* доступные бюджеты;
* лимиты показов.

Для Gateway credentials cache прогрев выполняется отдельно:

```text
Auth Cache Warmer
  -> Auth Service
  -> Gateway credentials cache
```

Что загружается:

* активные DSP-партнёры;
* статусы партнёров;
* hash API keys;
* allowlist IP;
* RPS-лимиты;
* версии credentials.

Прогрев не должен перегружать PostgreSQL. Данные нужно загружать пакетами и с ограничением скорости.

---

## 9. Поведение при сбоях Redis

Если Redis недоступен, Bidding Service не должен зависать.

Возможные действия:

| Ситуация                         | Действие                                                   |
| -------------------------------- | ---------------------------------------------------------- |
| Redis отвечает медленно          | Срабатывает timeout                                        |
| Redis часто ошибается            | Срабатывает Circuit Breaker                                |
| Нет данных по кампании           | Вернуть no-bid                                             |
| Нет данных по бюджету            | Вернуть no-bid                                             |
| Есть безопасные дефолтные данные | Использовать fallback, если это разрешено бизнес-правилами |

Для финансово чувствительных данных безопаснее вернуть `no-bid`, чем показать рекламу без актуального бюджета.

---

## 10. Поведение при сбоях Gateway credentials cache

Если Gateway credentials cache недоступен или не содержит нужных данных, Gateway должен деградировать безопасно.

Возможные действия:

| Ситуация                       | Действие                                       |
| ------------------------------ | ---------------------------------------------- |
| Кэш отвечает медленно          | Срабатывает timeout                            |
| Кэш недоступен                 | Gateway отклоняет неизвестные credentials      |
| Credentials не найдены         | Вернуть 401 или 403                            |
| Credentials просрочены         | Вернуть 401 или 403                            |
| Есть последняя валидная версия | Использовать только в пределах допустимого TTL |

Для неизвестных или просроченных credentials безопаснее отказать в доступе, чем пропустить внешний трафик в Bidding Service.

---

## 11. Ключи Redis

Пример структуры ключей для Bidding Service:

```text
campaign:{campaign_id}
campaign:{campaign_id}:targeting
campaign:{campaign_id}:bid
campaign:{campaign_id}:status
budget:{advertiser_id}
limit:{campaign_id}:daily
dsp:{dsp_id}:settings
```

Для списков активных кампаний можно использовать ключи:

```text
active_campaigns:{placement_id}
active_campaigns:{country}
active_campaigns:{device_type}
```

Так Bidding Service сможет быстрее находить подходящие кампании для конкретного bid request.

Для Gateway credentials cache можно использовать структуру:

```text
dsp:{dsp_id}:credentials
dsp:{dsp_id}:limits
dsp:{dsp_id}:allowlist
dsp:{dsp_id}:credentials:version
```

В этих ключах нельзя хранить секреты в открытом виде.

---

## 12. Метрики кэша

Для Redis и Cache Updater нужно собирать метрики:

* hit rate;
* miss rate;
* время ответа Redis;
* количество ошибок Redis;
* количество истёкших ключей;
* задержка обновления кэша после события;
* количество событий, которые не удалось обработать;
* размер кэша;
* количество срабатываний Circuit Breaker.

Для Gateway credentials cache нужно собирать:

* hit rate;
* miss rate;
* возраст данных;
* количество отклонённых credentials;
* задержку обновления после `auth-events`;
* ошибки Auth Cache Updater;
* количество устаревших записей;
* количество fallback-решений.

Эти метрики нужны, чтобы понимать, насколько кэши помогают и не устарели ли данные.

---

## 13. Безопасность

Пароли Redis и параметры подключения нельзя хранить в коде или репозитории.

Также нельзя хранить в репозитории:

* DSP API keys;
* JWT secrets;
* HMAC secrets;
* Kafka credentials;
* PostgreSQL credentials;
* `.env` файлы;
* приватные ключи и сертификаты.

Секреты нужно хранить:

* в переменных окружения;
* в Kubernetes Secret;
* в отдельном хранилище секретов.

Доступ к Redis должен быть только у сервисов, которым он действительно нужен:

* Bidding Service;
* Cache Updater;
* Cache Warmer;
* сервисы мониторинга.

Доступ к Gateway credentials cache нужен:

* DSP Gateway;
* Auth Cache Updater;
* сервисам мониторинга.

В кэше и логах не должно быть API keys, токенов и HMAC secrets в открытом виде. 
Для проверки нужно использовать hash или безопасное представление ключа.
