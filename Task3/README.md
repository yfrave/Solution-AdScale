# Task3 — Данные, масштабирование и отказоустойчивость

## Краткое описание

В рамках задачи проектируется стратегия работы с данными для микросервисной архитектуры AdScale.

После выделения отдельных сервисов важно разделить данные по зонам ответственности.
Каждый сервис должен владеть своими данными или использовать отдельную read-модель, если ему нужны быстрые 
данные для чтения.

Основные сервисы:

* **Bidding Service** — быстро рассчитывает ставку для DSP;
* **Campaign Service** — управляет кампаниями, ставками и таргетингом;
* **Tracking / Statistics Service** — принимает события показов, кликов и конверсий;
* **Analytics Service** — строит отчёты для рекламодателей;
* **Billing Service** — отвечает за балансы, списания и финансовые операции.

Для рабочих данных предлагается использовать PostgreSQL там, где нужна строгая консистентность и транзакции. 
Для аналитики предлагается использовать ClickHouse, потому что отчёты не должны нагружать рабочие базы. 
Для быстрых данных аукциона используется Redis. Для событий показов, кликов, ставок и финансовых изменений 
используется Kafka.

Основные решения:

* применить подход **Database per Service**;
* не использовать общую PostgreSQL для всех сервисов;
* использовать Redis как быструю read-модель для Bidding Service;
* хранить события в Kafka и обрабатывать их асинхронно;
* использовать ClickHouse для аналитики и отчётов;
* масштабировать базы через репликацию, шардирование и разделение чтения/записи;
* настроить резервное копирование и определить RPO/RTO для каждого сервиса.
