# Task3 — Данные, масштабирование и отказоустойчивость

## Краткое описание

В рамках задачи проектируется стратегия работы с данными для микросервисной архитектуры AdScale.

После выделения отдельных сервисов важно разделить данные по зонам ответственности. 
Каждый сервис должен владеть своими данными или использовать отдельную read-модель, если ему нужны быстрые данные для чтения.

Основные сервисы:

* **Auth Service** — управляет пользователями, ролями, JWT, refresh tokens и DSP credentials;
* **Bidding Service** — быстро рассчитывает ставку для DSP;
* **Campaign Service** — управляет кампаниями, ставками и таргетингом;
* **Tracking / Statistics Service** — принимает события показов, кликов и конверсий;
* **Analytics Service** — строит отчёты для рекламодателей;
* **Billing Service** — отвечает за балансы, списания и финансовые операции.

Для рабочих данных предлагается использовать PostgreSQL там, где нужна строгая консистентность и транзакции.

PostgreSQL используется для:

* `auth_db` — пользователи, роли, права доступа, refresh tokens и DSP credentials;
* `campaign_db` — кампании, ставки, таргетинг и креативы;
* `billing_db` — балансы, списания, платежи, счета и история операций.

Для аналитики предлагается использовать ClickHouse, потому что отчёты не должны нагружать рабочие базы.

Для быстрых данных аукциона используется Redis. В Redis хранится read-модель для Bidding Service: 
активные кампании, ставки, таргетинг, бюджеты, лимиты и статусы.

Для быстрой проверки DSP-партнёров используется Gateway credentials cache. 
Он хранит подготовленную read-модель DSP credentials и обновляется по событиям из Auth Service.

Для событий показов, кликов, ставок, изменений кампаний, бюджетов, финансовых операций и доступов используется Kafka.

Основные решения:

* применить подход **Database per Service**;
* не использовать общую PostgreSQL для всех сервисов;
* выделить `auth_db`, `campaign_db` и `billing_db`;
* использовать Redis как быструю read-модель для Bidding Service;
* использовать Gateway credentials cache для проверки DSP-партнёров;
* хранить события в Kafka и обрабатывать их асинхронно;
* использовать ClickHouse для аналитики и отчётов;
* масштабировать базы через репликацию, шардирование и разделение чтения/записи;
* настроить резервное копирование и определить RPO/RTO для каждого сервиса;
* описать поведение системы при сбоях Redis, Kafka, ClickHouse и PostgreSQL;
* реализовывать новые backend-сервисы и workers в едином стеке на Go.

## Основные хранилища

| Хранилище                 | Для чего используется                                                    |
| ------------------------- | ------------------------------------------------------------------------ |
| PostgreSQL `auth_db`      | пользователи, роли, права доступа, refresh tokens, DSP credentials       |
| PostgreSQL `campaign_db`  | кампании, ставки, таргетинг, креативы                                    |
| PostgreSQL `billing_db`   | балансы, платежи, списания, счета, история операций                      |
| Redis Cluster             | быстрая read-модель для Bidding Service                                  |
| Gateway credentials cache | read-модель DSP credentials для Gateway                                  |
| Kafka                     | события ставок, показов, кликов, кампаний, бюджетов, финансов и доступов |
| ClickHouse                | аналитика, агрегации и отчёты                                            |

## Основные потоки данных

### Данные кампаний

```text
Campaign Service
  -> campaign_db
  -> Kafka
  -> Cache Updater
  -> Redis
  -> Bidding Service
```

### Данные бюджетов

```text
Billing Service
  -> billing_db
  -> Kafka
  -> Cache Updater
  -> Redis
  -> Bidding Service
```

### Данные доступов DSP

```text
Auth Service
  -> auth_db
  -> Kafka
  -> Auth Cache Updater
  -> Gateway credentials cache
  -> DSP Gateway
```

### События статистики

```text
Bidding Service / Tracking Service
  -> Kafka
  -> Statistics Worker
  -> ClickHouse
  -> Analytics Service
```

## Принципы отказоустойчивости

Для разных типов данных используются разные подходы:

* PostgreSQL работает с репликацией, backup и WAL-архивированием;
* Redis и Gateway credentials cache считаются read-моделями и могут быть восстановлены из источников истины;
* Kafka использует replication factor, retention, consumer groups и DLQ;
* ClickHouse восстанавливается из backup и может догружать события из Kafka;
* финансовые операции защищаются идемпотентностью через `operation_id`;
* сервисы должны быть stateless и хранить состояние во внешних хранилищах.
