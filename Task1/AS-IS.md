# AS-IS анализ текущей архитектуры AdScale

## 1. Задача

Нужно проанализировать текущую архитектуру AdScale и понять, почему система уже не укладывается в требование 
по времени ответа.

AdScale — это рекламная платформа. Она принимает рекламные запросы от DSP-партнёров, выбирает подходящую рекламу, 
проводит аукцион ставок, показывает баннер пользователю, собирает клики и показы, а также даёт рекламодателям 
личный кабинет для управления кампаниями и бюджетами.

По условию система сейчас выдерживает пик примерно **15 000 RPS**, но уже есть проблема с задержками:

* требование: **P95 ≤ 100 ms**;
* сейчас: **P95 110–120 ms**.

То есть система уже работает хуже целевого показателя и в часы пик может деградировать.

---

## 2. Что есть сейчас

Сейчас AdScale выглядит как монолитное приложение, внутри которого есть несколько частей:

* **Ad Server** — принимает рекламные запросы и подбирает кандидатов на показ;
* **Auction Engine** — считает победителя аукциона;
* **Delivery Service** — формирует рекламный ответ и баннер;
* **Statistics Service** — записывает показы и клики;
* **Financial Service** — отвечает за балансы, списания и счета;
* **Analytics Service** — строит отчёты;
* **Advertiser Dashboard** — личный кабинет рекламодателя.

Все эти части используют одну общую базу данных **PostgreSQL**.

Также есть внешние системы:

* **DSP-партнёр** — отправляет запросы на участие в рекламном аукционе;
* **платёжный шлюз** — обрабатывает пополнение бюджета;
* **рекламодатель** — работает через личный кабинет;
* **пользователь сайта или приложения** — видит рекламу и кликает по ней.

---

## 3. Основной поток рекламного запроса

Основной сценарий выглядит так:

```text
DSP-партнёр
  -> Ad Server
  -> Auction Engine
  -> PostgreSQL
  -> Delivery Service
  -> Statistics Service
  -> PostgreSQL
```

Самое важное здесь то, что **Auction Engine ходит в PostgreSQL во время обработки рекламного запроса**.

Это проблема, потому что рекламный ответ должен быть очень быстрым. Если база данных отвечает медленно, 
то весь рекламный ответ тоже становится медленным.

---

## 4. Основные проблемы текущей архитектуры

### 4.1 Одна PostgreSQL используется для всего

Сейчас одна база данных используется сразу для разных задач:

* хранение кампаний;
* хранение ставок;
* запись показов и кликов;
* финансовые операции;
* аналитика;
* данные личного кабинета.

Из-за этого все части системы конкурируют за одну базу.

Например, в одно и то же время:

* Auction Engine читает ставки;
* Statistics Service пишет клики и показы;
* Analytics Service строит тяжёлый отчёт;
* Financial Service обновляет балансы;
* Advertiser Dashboard создаёт, читает и изменяет данные кампаний.

Получается, PostgreSQL становится главным узким местом.

---

### 4.2 База данных находится в критическом пути

Auction Engine синхронно читает данные из PostgreSQL.

Это плохо для рекламной платформы, потому что аукцион должен работать быстро. Если каждый рекламный запрос 
ждёт базу данных, то при росте нагрузки задержки будут расти.

Из-за этого текущий P95 уже стал **110–120 ms** вместо требуемых **100 ms**.

---

### 4.3 Статистика пишется напрямую в PostgreSQL

Показы и клики записываются напрямую в базу данных.

Но такие события могут идти большим потоком. При высокой нагрузке они создают много операций записи.

Проблема в том, что эти записи идут в ту же базу, из которой Auction Engine читает данные для аукциона. 
Поэтому статистика может мешать показу рекламы.

Лучше было бы принимать события быстро и складывать их в очередь или брокер сообщений, а потом обрабатывать отдельно.

---

### 4.4 Аналитика выполняется по основной рабочей базе данных

Analytics Service строит отчёты по той же базе данных, которая используется для основной работы системы.

Отчёты обычно тяжёлые: там могут быть группировки, сортировки и выборки за большие периоды.

Из-за этого аналитика может нагружать PostgreSQL и влиять на обработку рекламных запросов.

То есть рекламодатель может открыть тяжёлый отчёт, и это потенциально ухудшит работу рекламного аукциона.

---

### 4.5 Нет кэша

В системе указано, что кэширование отсутствует.

Это значит, что часто используемые данные каждый раз читаются из PostgreSQL:

* активные кампании;
* ставки;
* таргетинг;
* статусы кампаний;
* бюджеты.

Для таких данных лучше использовать кэш, например Redis. Тогда Auction Engine сможет быстро получать нужные данные 
и не обращаться каждый раз к PostgreSQL.

---

### 4.6 Нет очередей и асинхронной обработки

В системе нет асинхронных очередей.

Из-за этого все операции выполняются напрямую и синхронно. Если один компонент начинает тормозить, 
это может повлиять на остальные.

Очереди или брокер сообщений нужны хотя бы для:

* показов;
* кликов;
* конверсий;
* изменений кампаний;
* финансовых событий.

Это помогло бы сглаживать пики нагрузки и не давить сразу на базу данных.

---

### 4.7 Нет отказоустойчивости базы данных

PostgreSQL указана как одна инстанция. Нет отказоустойчивой конфигурации и реплик для чтения.

Это значит, что база данных является единой точкой отказа.

Если PostgreSQL станет недоступной, то фактически пострадает вся система:

* аукцион;
* показ рекламы;
* статистика;
* финансы;
* личный кабинет;
* аналитика.

---

### 4.8 Ручной деплой

В легенде указано, что деплой выполняется вручную и без контейнеризации.

Это не основная причина медленной работы, но это проблема для развития системы.

Ручной деплой повышает риск ошибок и усложняет масштабирование. Если в будущем систему будут делить на сервисы, 
без автоматической сборки, проверки и деплоя это будет делать сложно.

---

## 5. Узкие места

Главные узкие места текущей архитектуры:

| Узкое место         | Почему это проблема                              |
| ------------------- | ------------------------------------------------ |
| PostgreSQL          | Через неё проходит почти вся нагрузка            |
| Auction Engine      | Находится в критическом пути и зависит от БД     |
| Statistics Service  | Пишет много событий напрямую в БД                |
| Analytics Service   | Выполняет тяжёлые запросы по основной рабочей БД |
| Отсутствие кэша     | Все чтения идут напрямую в PostgreSQL            |
| Отсутствие очередей | Нет буфера для пиков нагрузки                    |

---

## 6. Точки отказа

Основные точки отказа:

| Точка отказа       | Что будет при сбое                                    |
| ------------------ | ----------------------------------------------------- |
| PostgreSQL         | Может остановиться почти вся платформа                |
| Auction Engine     | Нельзя будет выбрать победителя аукциона              |
| Ad Server          | Нельзя будет нормально принимать рекламные запросы    |
| Statistics Service | Клики и показы могут не записываться                  |
| Financial Service  | Возникнут проблемы с бюджетами и списаниями           |
| Analytics Service  | Отчёты могут стать недоступны или начать тормозить БД |

Самая опасная точка отказа — это PostgreSQL, потому что она одна и используется всеми частями системы.

---

## 7. Влияние на время ответа

Текущая архитектура напрямую влияет на время ответа.

Основные причины:

1. **Auction Engine ждёт PostgreSQL.**
   Если база отвечает медленно, рекламный ответ тоже становится медленным.

2. **Статистика создаёт большую нагрузку на запись.**
   Показы и клики пишутся в ту же базу, которая нужна для аукциона.

3. **Аналитика нагружает основную рабочую БД.**
   Тяжёлые отчёты могут мешать обычным рекламным запросам.

4. **Нет кэша.**
   Даже часто используемые данные читаются из базы данных.

5. **Нет очередей.**
   Нагрузка не сглаживается, а сразу попадает в основные компоненты.

Поэтому P95 уже вырос до **110–120 ms**, хотя нужно не больше **100 ms**.

---

## 8. Причины проблем

Можно связать симптомы и причины так:

| Симптом                               | Возможная причина                                  |
| ------------------------------------- | -------------------------------------------------- |
| P95 выше требования                   | Синхронные запросы к PostgreSQL в критическом пути |
| Деградации в часы пик                 | Все виды нагрузки идут в одну БД                   |
| Нет запаса по производительности      | Нет кэша и очередей                                |
| Сложно масштабировать систему         | Все части находятся внутри монолита                |
| Аналитика влияет на обработку рекламы | Отчёты выполняются по основной рабочей БД          |
| Высокий риск отказа                   | PostgreSQL одна, без отказоустойчивости и реплик   |

---

## 9. Что можно улучшить

На основе анализа можно предложить несколько направлений улучшения:

1. **Добавить кэш для данных аукциона.**
   Например, хранить активные кампании, ставки и бюджеты в Redis.

2. **Убрать PostgreSQL из критического пути.**
   Auction Engine не должен каждый раз ходить в базу при обработке рекламного запроса.

3. **Добавить брокер сообщений.**
   Показы и клики лучше отправлять в Kafka, а потом обрабатывать асинхронно.

4. **Отделить аналитику от основной рабочей БД.**
   Для отчётов лучше использовать отдельное аналитическое хранилище, возможно колоночное решение ClickHouse.

5. **Постепенно выделять сервисы.**
   В первую очередь стоит выделять те части, которые сильнее всего влияют на время ответа и нагрузку: аукцион, статистику и аналитику.

6. **Настроить автоматическую сборку, проверку и деплой.**
   Это нужно для более безопасного деплоя и дальнейшего масштабирования.
