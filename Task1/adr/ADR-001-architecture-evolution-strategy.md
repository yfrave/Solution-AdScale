# ADR-001: Стратегия эволюции архитектуры AdScale

**Дата:** 2026-06-18

**Статус:** Предложено

---

## 1. Контекст

AdScale сейчас работает как монолитное приложение с одной общей PostgreSQL.

Внутри монолита находятся основные части системы:

* Ad Server;
* Auction Engine;
* Delivery Service;
* Statistics Service;
* Financial Service;
* Analytics Service;
* Advertiser Dashboard.

Текущая архитектура уже не укладывается в требование по времени ответа:

* пиковая нагрузка — около **15 000 RPS**;
* требование — **P95 ≤ 100 ms**;
* сейчас — **P95 110–120 ms**.

Главные проблемы текущей архитектуры:

* Auction Engine обращается к PostgreSQL во время обработки рекламного запроса;
* показы и клики пишутся напрямую в основную PostgreSQL;
* аналитика строит тяжёлые отчёты по той же базе;
* одна PostgreSQL используется почти всеми частями системы;
* нет кэша;
* нет брокера сообщений;
* деплой выполняется вручную.

Из-за этого PostgreSQL стала главным узким местом и единой точкой отказа.

---

## 2. Рассмотренные варианты

### Вариант 1. Оставить текущий монолит

Можно оставить систему как есть и попробовать оптимизировать её внутри текущей архитектуры.

Плюсы:

* меньше изменений;
* ниже риск быстрой поломки;
* не нужно сразу перестраивать процессы разработки и деплоя.

Минусы:

* монолит сложно масштабировать по частям;
* Auction Engine всё равно зависит от PostgreSQL;
* статистика и аналитика продолжают мешать основной работе системы;
* одна PostgreSQL остаётся единой точкой отказа;
* проблема с P95 может быстро вернуться при росте нагрузки.

Этот вариант не решает главные архитектурные проблемы.

---

### Вариант 2. Сразу переписать систему на микросервисы

Можно полностью переписать AdScale и сразу выделить все части в отдельные микросервисы.

Плюсы:

* можно получить независимое масштабирование сервисов;
* можно разделить базы данных;
* можно лучше изолировать статистику, финансы и аналитику.

Минусы:

* система уже работает, её нельзя просто остановить;
* высокий риск сломать текущие интеграции с DSP-партнёрами и платёжным шлюзом;
* можно потерять часть бизнес-логики из монолита;
* резко вырастет сложность разработки и сопровождения;
* без автоматического деплоя и мониторинга микросервисы будет сложно поддерживать;
* результат появится не сразу, а проблема с задержками уже есть сейчас.

Этот вариант слишком рискованный для текущего состояния системы.

---

### Вариант 3. Постепенно развивать архитектуру

Можно использовать постепенный переход от монолита к сервисной архитектуре.

Смысл подхода: не переписывать всю систему сразу, а постепенно выносить из монолита самые проблемные части.

В первую очередь нужно:

* добавить Redis для быстрых данных аукциона;
* убрать PostgreSQL из критического пути рекламного запроса;
* отправлять показы и клики в Kafka;
* строить отчёты через ClickHouse;
* постепенно выделять сервисы аукциона, кампаний, статистики, финансов и аналитики.

Плюсы:

* можно снижать риски поэтапно;
* можно быстрее улучшить время ответа;
* можно не ломать внешние интеграции;
* можно постепенно подготовить деплой, мониторинг и контейнеризацию;
* можно выделять сервисы только там, где это действительно нужно.

Минусы:

* переход займёт время;
* часть монолита ещё какое-то время останется;
* потребуется поддерживать старую и новую архитектуру одновременно;
* нужна дисциплина при разделении данных и ответственности сервисов.

Этот вариант лучше всего подходит для AdScale.

---

## 3. Решение

Предлагается стратегия постепенной эволюции архитектуры AdScale от монолита к набору отдельных сервисов.

Основной подход — **Strangler Fig Pattern**.

Это значит, что монолит не переписывается полностью за один этап. Вместо этого новые сервисы постепенно забирают 
на себя отдельные функции.

Целевое направление развития:

1. Добавить **Gateway** как единую точку входа.
2. Добавить **Redis** для данных, которые нужны рекламному аукциону.
3. Добавить **Kafka** для событий показов, кликов, конверсий и изменений кампаний.
4. Добавить **ClickHouse** для аналитики и отчётов.
5. Постепенно выделить:

    * сервис рекламного аукциона;
    * сервис кампаний;
    * сервис статистики;
    * сервис финансов;
    * сервис аналитики.
6. Разделить данные по назначению:

    * `campaign_db` — кампании, ставки, таргетинг;
    * `billing_db` — балансы, списания, счета;
    * ClickHouse — аналитика и отчёты;
    * Redis — быстрые данные для аукциона;
    * Kafka — поток событий.

Главная цель решения — убрать самые нагруженные и критичные части из общей PostgreSQL и дать системе возможность 
масштабироваться по частям.

---

## 4. Последствия

### Положительные последствия

* Auction Engine перестаёт каждый раз обращаться к PostgreSQL в критическом пути.
* Redis снижает задержку рекламного аукциона.
* Kafka снижает прямую нагрузку статистики на PostgreSQL.
* ClickHouse отделяет тяжёлые аналитические отчёты от основной рабочей базы.
* Финансовая часть получает отдельную область ответственности.
* Сервисы можно будет масштабировать отдельно.
* Внешние клиенты не зависят от внутренних изменений, потому что перед ними находится Gateway.

---

### Отрицательные последствия

* Архитектура станет сложнее.
* Появятся новые компоненты: Redis, Kafka, ClickHouse, Gateway.
* Нужно будет настраивать мониторинг новых компонентов.
* Нужно будет поддерживать часть старого монолита и новые сервисы одновременно.
* Команде потребуется аккуратно разделять данные и не возвращаться к общей базе для всех сервисов.

---

### Риски

* Если сервисы будут продолжать напрямую читать общую PostgreSQL, получится распределённый монолит.
* Если не настроить мониторинг Kafka и Redis, проблемы могут стать менее заметными.
* Если события из Kafka будут обрабатываться с задержкой, отчёты и бюджеты могут обновляться не сразу.
* Если не настроить автоматический деплой, развитие сервисов будет рискованным.
* Секреты для баз данных, Kafka, Redis и платёжного шлюза нельзя хранить в коде или в репозитории. 
Их нужно выносить в безопасное хранилище секретов или переменные окружения.

---

## 5. Итог

AdScale будет развиваться постепенно: от текущего монолита к сервисной архитектуре.

Сначала нужно убрать самые проблемные места:

* PostgreSQL из критического пути рекламного запроса;
* прямую запись показов и кликов в основную БД;
* тяжёлую аналитику по рабочей PostgreSQL.

После этого можно постепенно выделять отдельные сервисы.

Такой подход снижает риски и позволяет улучшать архитектуру без полной остановки работающей рекламной платформы.
