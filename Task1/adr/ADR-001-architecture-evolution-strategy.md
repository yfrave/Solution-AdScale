# ADR-001: Стратегия эволюции архитектуры AdScale

**Дата:** 2026-06-18

**Статус:** Предложено

---

## 1. Контекст

AdScale сейчас работает как монолитное приложение с одной общей PostgreSQL.

Внутри монолита находятся основные части системы:

* Ad Server;
* Auction Engine;
* Delivery Service;
* Statistics Service;
* Financial Service;
* Analytics Service;
* Advertiser Dashboard;
* логика пользователей, ролей и доступов;
* данные DSP-партнёров и ключей интеграции.

Текущая архитектура уже не укладывается в требование по времени ответа:

* пиковая нагрузка — около **15 000 RPS**;
* требование — **P95 ≤ 100 ms**;
* сейчас — **P95 110–120 ms**.

Главные проблемы текущей архитектуры:

* Auction Engine обращается к PostgreSQL во время обработки рекламного запроса;
* показы и клики пишутся напрямую в основную PostgreSQL;
* аналитика строит тяжёлые отчёты по той же базе;
* одна PostgreSQL используется почти всеми частями системы;
* авторизация, роли, права доступа и DSP credentials находятся внутри монолита;
* нет кэша;
* нет брокера сообщений;
* деплой выполняется вручную.

Из-за этого PostgreSQL стала главным узким местом и единой точкой отказа.

Также при дальнейшем выделении сервисов появляется отдельная архитектурная проблема: 
новым сервисам нужен единый способ проверки пользователей, ролей и DSP-партнёров. 
Если не решить это заранее, логика доступа начнёт дублироваться в каждом сервисе,
Gateway не сможет стать полноценной контролируемой точкой входа.

---

## 2. Рассмотренные варианты

### Вариант 1. Оставить текущий монолит

Можно оставить систему как есть и попробовать оптимизировать её внутри текущей архитектуры.

Плюсы:

* меньше изменений;
* ниже риск быстрой поломки;
* не нужно сразу перестраивать процессы разработки и деплоя.

Минусы:

* монолит сложно масштабировать по частям;
* Auction Engine всё равно зависит от PostgreSQL;
* статистика и аналитика продолжают мешать основной работе системы;
* одна PostgreSQL остаётся единой точкой отказа;
* авторизация и управление доступами остаются связанными с монолитом;
* проблема с P95 может быстро вернуться при росте нагрузки.

Этот вариант не решает главные архитектурные проблемы.

---

### Вариант 2. Сразу переписать систему на микросервисы

Можно полностью переписать AdScale и сразу выделить все части в отдельные микросервисы.

Плюсы:

* можно получить независимое масштабирование сервисов;
* можно разделить базы данных;
* можно лучше изолировать статистику, финансы, доступы и аналитику.

Минусы:

* система уже работает, её нельзя просто остановить;
* высокий риск сломать текущие интеграции с DSP-партнёрами и платёжным шлюзом;
* можно потерять часть бизнес-логики из монолита;
* резко вырастет сложность разработки и сопровождения;
* без автоматического деплоя и мониторинга микросервисы будет сложно поддерживать;
* результат появится не сразу, а проблема с задержками уже есть сейчас.

Этот вариант слишком рискованный для текущего состояния системы.

---

### Вариант 3. Постепенно развивать архитектуру

Можно использовать постепенный переход от монолита к сервисной архитектуре.

Смысл подхода: не переписывать всю систему сразу, а постепенно выносить из монолита самые проблемные и базовые части.

В первую очередь нужно:

* добавить Gateway как управляемую точку входа;
* выделить Auth Service для пользователей, ролей, JWT, refresh tokens и DSP credentials;
* добавить Redis для быстрых данных аукциона;
* убрать PostgreSQL из критического пути рекламного запроса;
* отправлять показы и клики в Kafka;
* строить отчёты через ClickHouse;
* постепенно выделять сервисы аукциона, кампаний, статистики, финансов и аналитики.

Плюсы:

* можно снижать риски поэтапно;
* можно быстрее улучшить время ответа;
* можно не ломать внешние интеграции;
* можно постепенно подготовить деплой, мониторинг и контейнеризацию;
* можно выделять сервисы только там, где это действительно нужно;
* можно заранее создать единый контур безопасности и доступа для новых сервисов.

Минусы:

* переход займёт время;
* часть монолита ещё какое-то время останется;
* потребуется поддерживать старую и новую архитектуру одновременно;
* нужна дисциплина при разделении данных и ответственности сервисов.

Этот вариант лучше всего подходит для AdScale.

---

## 3. Решение

Предлагается стратегия постепенной эволюции архитектуры AdScale от монолита к набору отдельных сервисов.

Основной подход — **Strangler Fig Pattern**.

Это значит, что монолит не переписывается полностью за один этап. Вместо этого новые сервисы постепенно забирают на себя отдельные функции.

Целевое направление развития:

1. Добавить **Gateway** как единую точку входа для внешних запросов.

2. Выделить **Auth Service** как единый сервис пользователей, ролей, JWT, refresh tokens и DSP credentials.

3. Выделить отдельную базу `auth_db`.

4. Добавить Gateway credentials cache для быстрой проверки DSP-партнёров.

5. Добавить **Redis** для данных, которые нужны рекламному аукциону.

6. Добавить **Kafka** для событий показов, кликов, конверсий, изменений кампаний, бюджетов и доступов.

7. Добавить **ClickHouse** для аналитики и отчётов.

8. Постепенно выделить:

   * сервис рекламного аукциона;
   * сервис кампаний;
   * сервис статистики;
   * сервис финансов;
   * сервис аналитики.

9. Разделить данные по назначению:

   * `auth_db` — пользователи, роли, права доступа, refresh tokens, DSP credentials;
   * `campaign_db` — кампании, ставки, таргетинг;
   * `billing_db` — балансы, списания, счета;
   * ClickHouse — аналитика и отчёты;
   * Redis — быстрые данные для аукциона;
   * Gateway credentials cache — быстрая read-модель DSP credentials;
   * Kafka — поток событий.

Главная цель решения — убрать самые нагруженные и критичные части из общей PostgreSQL и дать системе возможность масштабироваться по частям.

## 4. Почему Auth Service выделяется на первом этапе

Auth Service стоит выделять на первом этапе не только из-за безопасности.

Главная причина — он создаёт **единый управляемый контур доступа** для всей будущей сервисной архитектуры.

При постепенном выделении сервисов через Strangler Fig Pattern сначала появляется Gateway, а затем за ним начинают появляться новые сервисы. Если к этому моменту нет отдельного Auth Service, каждый новый сервис будет вынужден самостоятельно решать вопросы пользователей, ролей, токенов, DSP-партнёров и ключей доступа.

Это приведёт к нескольким проблемам:

* дублирование логики авторизации в разных сервисах;
* разные правила проверки доступа в разных частях системы;
* сложная ротация DSP API keys;
* сложная блокировка DSP-партнёров;
* повышенный риск ошибок безопасности;
* зависимость новых сервисов от монолита для проверки доступа.

Поэтому Auth Service выделяется как базовый слой для дальнейшей декомпозиции.

Он позволяет:

* сделать Gateway полноценной контролируемой точкой входа;
* централизованно управлять пользователями, ролями и DSP-партнёрами;
* не переносить логику доступа в каждый новый сервис отдельно;
* подключать новые сервисы за Gateway по единой схеме;
* безопасно развивать RTB-интеграцию с внешними DSP;
* отделить бизнес-логику аукциона, кампаний и финансов от логики доступа.

Для RTB-пути Auth Service не должен быть синхронной зависимостью на каждый bid request. 
Данные DSP credentials обновляются через Kafka и используются Gateway в виде быстрой read-модели.

Поток обновления:

```text
Auth Service
  -> auth_db
  -> Kafka
  -> Auth Cache Updater
  -> Gateway credentials cache
```

Такой подход даёт единый контур доступа, но не увеличивает задержку рекламного аукциона.

## 5. Последствия

### Положительные последствия

* Auction Engine перестаёт каждый раз обращаться к PostgreSQL в критическом пути.
* Redis снижает задержку рекламного аукциона.
* Kafka снижает прямую нагрузку статистики на PostgreSQL.
* ClickHouse отделяет тяжёлые аналитические отчёты от основной рабочей базы.
* Auth Service создаёт единый контур управления пользователями, ролями и DSP credentials.
* Gateway получает единую схему проверки внешних запросов.
* Финансовая часть получает отдельную область ответственности.
* Сервисы можно будет масштабировать отдельно.
* Внешние клиенты не зависят от внутренних изменений, потому что перед ними находится Gateway.
* Новые backend-сервисы можно развивать в едином стеке на Go.

---

### Отрицательные последствия

* Архитектура станет сложнее.
* Появятся новые компоненты: Gateway, Auth Service, Redis, Kafka, ClickHouse.
* Нужно будет настраивать мониторинг новых компонентов.
* Нужно будет поддерживать часть старого монолита и новые сервисы одновременно.
* Команде потребуется аккуратно разделять данные и не возвращаться к общей базе для всех сервисов.
* Появится необходимость управлять согласованностью read-моделей, которые обновляются через Kafka.

---

### Риски

* Если сервисы будут продолжать напрямую читать общую PostgreSQL, получится распределённый монолит.
* Если каждый сервис начнёт сам реализовывать логику доступа, появятся дублирование и расхождения в правилах авторизации.
* Если не настроить мониторинг Kafka и Redis, проблемы могут стать менее заметными.
* Если события из Kafka будут обрабатываться с задержкой, отчёты, бюджеты и read-модели могут обновляться не сразу.
* Если Gateway credentials cache будет устаревать слишком долго, возможны задержки в применении блокировок и ротации ключей.
* Если не настроить автоматический деплой, развитие сервисов будет рискованным.
* Секреты для баз данных, Kafka, Redis, DSP, JWT и платёжного шлюза нельзя хранить в коде или в репозитории. 
* Их нужно выносить в безопасное хранилище секретов или переменные окружения.

---

## 6. Принятые архитектурные ограничения

Для целевой архитектуры фиксируются следующие ограничения:

* новые backend-сервисы реализуются в едином стеке на Go;
* Gateway используется как единая внешняя точка входа;
* сервисы не читают базы данных друг друга напрямую;
* PostgreSQL не используется в критическом пути рекламного аукциона;
* события передаются через Kafka;
* аналитические отчёты строятся из ClickHouse;
* Redis и Gateway credentials cache являются read-моделями, а не источниками истины;
* секреты не хранятся в коде и репозитории.

---

## 7. Итог

AdScale будет развиваться постепенно: от текущего монолита к сервисной архитектуре.

Сначала нужно убрать самые проблемные места:

* PostgreSQL из критического пути рекламного запроса;
* прямую запись показов и кликов в основную БД;
* тяжёлую аналитику по рабочей PostgreSQL;
* смешение бизнес-логики и логики доступа внутри монолита.

После этого можно постепенно выделять отдельные сервисы.

Первый этап должен создать основу для дальнейшей декомпозиции:

* Gateway;
* Auth Service;
* Redis read-модель для аукциона;
* Kafka для событий;
* ClickHouse для аналитики.

Такой подход снижает риски и позволяет улучшать архитектуру без полной остановки работающей рекламной платформы.
