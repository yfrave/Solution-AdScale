# TO-BE целевая архитектура AdScale

## 1. Задача

Нужно описать, как может выглядеть целевая архитектура AdScale через год.

По AS-IS анализу видно, что главные проблемы текущей системы такие:

* одна PostgreSQL используется почти для всего;
* Auction Engine обращается к PostgreSQL во время обработки рекламного запроса;
* статистика показов и кликов пишется напрямую в основную БД;
* аналитика строит тяжёлые отчёты по той же БД;
* нет кэша;
* нет очередей;
* деплой выполняется вручную.

Из-за этого система уже не укладывается в требование по времени ответа: сейчас **P95 110–120 ms**,
а нужно **не больше 100 ms**.

---

## 2. Выбор подхода

Для развития системы лучше выбрать постепенную замену частей монолита новыми сервисами.

Такой подход обычно называют **Strangler Fig Pattern**. Смысл простой: не переписывать всю систему сразу,
а постепенно выносить из монолита самые проблемные части.

---

## 3. Почему не оставить текущий монолит

Оставить систему как есть нельзя, потому что проблемы уже проявились на текущей нагрузке.

Основные причины:

* монолит сложно масштабировать по частям;
* все части используют одну PostgreSQL;
* аукцион зависит от скорости работы базы данных;
* статистика и аналитика мешают основной работе системы;
* авторизация, кампании, финансы и аналитика связаны внутри одной системы;
* сбой PostgreSQL может повлиять почти на всю платформу;
* ручной деплой усложняет развитие.

То есть текущий монолит можно временно оптимизировать, но это не решит главные архитектурные проблемы.

---

## 4. Почему не стоит сразу переписывать всё на микросервисы

Полностью переписать систему на микросервисы сразу тоже плохая идея.

Причины:

* система уже работает, её нельзя просто остановить;
* можно сломать текущие интеграции с DSP-партнёрами и платёжным шлюзом;
* можно потерять часть бизнес-логики из монолита;
* резко вырастет сложность разработки и поддержки;
* без автоматического деплоя и мониторинга микросервисы будет сложно сопровождать;
* результат появится не сразу, а проблема со временем ответа есть уже сейчас.

Поэтому лучше двигаться постепенно.

---

## 5. Общая идея целевой архитектуры

Целевая архитектура должна убрать самые проблемные места:

1. Данные для аукциона нужно читать из кэша, а не каждый раз из PostgreSQL.
2. Показы и клики нужно отправлять в брокер сообщений.
3. Аналитику нужно строить по отдельному хранилищу.
4. Финансовую часть нужно отделить от статистики и аналитики.
5. Авторизацию и управление доступами нужно вынести в отдельный Auth Service.
6. Самые нагруженные части нужно постепенно выделять в отдельные сервисы.

---

## 6. Основные компоненты целевой архитектуры

### 6.1 Gateway

Gateway становится единой точкой входа для внешних запросов.

Через него проходят:

* рекламные запросы от DSP-партнёров;
* запросы из личного кабинета;
* события показов и кликов.

Gateway нужен, чтобы скрыть внутренние изменения системы от внешних клиентов.

Также Gateway выполняет инфраструктурные функции:

* маршрутизацию запросов;
* проверку токенов и ключей доступа;
* rate limiting;
* логирование;
* сбор метрик;
* контроль таймаутов.

Для рекламных запросов от DSP Gateway не должен каждый раз синхронно обращаться в Auth Service, 
потому что это увеличит задержку в критическом пути. Данные для проверки DSP-ключей можно кэшировать на стороне Gateway.

---

### 6.2 Auth Service

Auth Service отвечает за авторизацию и управление доступами.

Он нужен для:

* входа рекламодателей в личный кабинет;
* выпуска и проверки JWT-токенов;
* хранения пользователей;
* хранения ролей и прав доступа;
* управления API keys для DSP-партнёров;
* управления сервисными credentials для внутренних интеграций.

У Auth Service должна быть отдельная база данных `auth_db`.

Для DSP-запросов правильный поток такой:

```text
DSP-партнёр
  -> Gateway
  -> проверка API key / HMAC / allowlist IP по кэшу Gateway
  -> Сервис рекламного аукциона
```

Для рекламодателя поток такой:

```text
Рекламодатель
  -> Личный кабинет
  -> Auth Service
  -> JWT token
  -> Сервисы AdScale через Gateway
```

Такой подход отделяет безопасность от бизнес-логики ставок и не замедляет обработку bid request.

---

### 6.3 Сервис рекламного аукциона

Сервис рекламного аукциона отвечает за выбор победителя.

Он должен:

* получать рекламный запрос;
* брать данные кампаний, ставок и бюджетов из Redis;
* рассчитывать победителя аукциона;
* отдавать результат дальше в Delivery Service.

Главное изменение: сервис аукциона не должен каждый раз ходить в PostgreSQL во время обработки рекламного запроса.

Также сервис аукциона не должен синхронно обращаться в Auth Service на каждый bid request. 
Проверка DSP-партнёра должна выполняться на уровне Gateway.

---

### 6.4 Сервис кампаний

Сервис кампаний отвечает за:

* создание кампаний;
* изменение ставок;
* настройку таргетинга;
* запуск и остановку кампаний;
* хранение данных о кампаниях.

У этого сервиса должна быть своя база данных `campaign_db`.

Когда рекламодатель меняет кампанию, сервис публикует событие. После этого данные в Redis обновляются
для быстрого использования в аукционе.

---

### 6.5 Redis для быстрых данных

Redis используется как кэш для данных, которые часто нужны аукциону:

* активные кампании;
* ставки;
* таргетинг;
* статусы кампаний;
* бюджеты;
* настройки DSP-партнёров, если они нужны для быстрой проверки на Gateway.

Это позволит снизить нагрузку на PostgreSQL и ускорить обработку рекламного запроса.

Redis не является источником истины. Основные данные хранятся в сервисах-владельцах:

* кампании — в `campaign_db`;
* финансы — в `billing_db`;
* пользователи, роли и DSP-ключи — в `auth_db`.

---

### 6.6 Сервис статистики

Сервис статистики принимает:

* показы;
* клики;
* конверсии.

Он не должен писать эти события напрямую в PostgreSQL. Вместо этого он отправляет их в Kafka.

Так система сможет быстро принимать события и обрабатывать их отдельно.

---

### 6.7 Kafka

Kafka используется как брокер сообщений.

Через Kafka можно передавать:

* показы;
* клики;
* конверсии;
* изменения кампаний;
* изменения бюджетов;
* финансовые события;
* события изменения DSP-ключей и прав доступа, если нужно обновлять кэш Gateway.

Это нужно, чтобы сглаживать пики нагрузки и не давить сразу на базу данных.

---

### 6.8 Обработчик статистики

Отдельный обработчик читает события из Kafka, считает показы, клики, расходы и конверсии, а затем записывает подготовленные данные в ClickHouse.

---

### 6.9 Сервис финансов

Сервис финансов отвечает за:

* балансы рекламодателей;
* пополнение бюджета;
* списания;
* счета;
* историю операций.

У него должна быть отдельная база данных `billing_db`.

Финансы лучше отделить, потому что ошибки в этой части критичны для бизнеса.

Финансовые операции должны быть идемпотентными, чтобы повторная обработка события не привела к повторному списанию.

---

### 6.10 Сервис аналитики

Сервис аналитики отвечает за отчёты рекламодателей.

Он читает данные из ClickHouse, а не из основной PostgreSQL. За счёт этого тяжёлые отчёты не мешают обработке рекламных запросов.

---

### 6.11 Личный кабинет рекламодателя

Личный кабинет остаётся интерфейсом для рекламодателя.

Через него рекламодатель может:

* войти в систему;
* управлять кампаниями;
* менять ставки;
* пополнять бюджет;
* смотреть отчёты.

Личный кабинет больше не должен напрямую работать с общей PostgreSQL. Он должен обращаться
к отдельным сервисам через API.

Авторизация рекламодателя проходит через Auth Service.

---

## 7. Основные потоки данных

### 7.1 Вход рекламодателя в личный кабинет

```text
Рекламодатель
  -> Личный кабинет
  -> Gateway
  -> Auth Service
  -> auth_db
  -> JWT token
  -> Личный кабинет
```

После успешного входа личный кабинет использует JWT-токен для обращений к Campaign Service, 
Billing Service и Analytics Service.

---

### 7.2 Обработка рекламного запроса

```text
DSP-партнёр
  -> Gateway
  -> проверка DSP credentials по кэшу Gateway
  -> Сервис рекламного аукциона
  -> Redis
  -> Delivery Service
  -> Ответ с рекламой
```

Главное отличие от текущей архитектуры: в этом сценарии нет синхронного обращения к PostgreSQL 
и нет синхронного обращения к Auth Service.

Это важно, потому что рекламный запрос находится в критическом пути и должен укладываться в требование по времени ответа.

---

### 7.3 Запись показов и кликов

```text
Пользователь / Delivery Service
  -> Сервис статистики
  -> Kafka
  -> Обработчик статистики
  -> ClickHouse
```

Главное отличие: показы и клики не пишутся напрямую в основную PostgreSQL.

---

### 7.4 Изменение кампании

```text
Личный кабинет
  -> Gateway
  -> проверка JWT
  -> Сервис кампаний
  -> campaign_db
  -> Kafka
  -> Обновление Redis
  -> Сервис рекламного аукциона
```

Так изменения кампаний будут попадать в быстрый кэш для аукциона.

---

### 7.5 Пополнение бюджета

```text
Личный кабинет
  -> Gateway
  -> проверка JWT
  -> Сервис финансов
  -> Платёжный шлюз
  -> billing_db
  -> Kafka
  -> Обновление бюджета в Redis
```

Финансовые данные хранятся отдельно, а в Redis попадает только информация, нужная для быстрого расчёта аукциона.

---

### 7.6 Обновление DSP API keys

```text
Администратор / Личный кабинет
  -> Gateway
  -> Auth Service
  -> auth_db
  -> Kafka
  -> Обновление кэша Gateway
```

Так Gateway сможет быстро проверять DSP-партнёров без синхронного запроса в Auth Service на каждый bid request.

---

## 8. Хранилища данных

В целевой архитектуре данные лучше разделить по назначению.

| Хранилище     | Что хранит                                                      |
| ------------- | --------------------------------------------------------------- |
| `auth_db`     | Пользователи, роли, права доступа, refresh tokens, DSP API keys |
| `campaign_db` | Кампании, ставки, таргетинг                                     |
| `billing_db`  | Балансы, списания, счета                                        |
| ClickHouse    | Данные для аналитики и отчётов                                  |
| Redis         | Быстрые данные для аукциона и кэш некоторых проверок            |
| Kafka         | Поток событий                                                   |

Такое разделение нужно, чтобы разные части системы не мешали друг другу.

Важно: пароли, токены, приватные ключи и секреты DSP нельзя хранить в репозитории. 
Их нужно хранить в переменных окружения, Kubernetes Secret или отдельном хранилище секретов. 
В базе нельзя хранить API keys в открытом виде, храним их хэши.

---

## 9. Этапы перехода

### Этап 1. Подготовка

На первом этапе нужно:

* добавить мониторинг;
* найти самые медленные запросы;
* настроить автоматическую сборку и деплой;
* подготовить контейнеризацию;
* описать текущие сценарии авторизации и доступа.

---

### Этап 2. Добавить кэш

Данные, которые нужны для аукциона, нужно вынести в Redis.

Это должно снизить количество обращений к PostgreSQL.

---

### Этап 3. Добавить Kafka для событий

Показы и клики нужно отправлять в Kafka.

Это снизит нагрузку на основную БД и позволит обрабатывать статистику отдельно.

---

### Этап 4. Отделить авторизацию

Авторизацию и управление доступами нужно вынести в Auth Service.

На этом этапе нужно:

* вынести пользователей, роли и права доступа в `auth_db`;
* настроить JWT для личного кабинета;
* описать API keys для DSP-партнёров;
* добавить кэширование DSP credentials на Gateway;
* не добавлять синхронный вызов Auth Service в критический путь bid request.

---

### Этап 5. Отделить аналитику

Отчёты нужно строить по отдельному аналитическому хранилищу на ClickHouse.

Это нужно, чтобы тяжёлые отчёты не мешали рекламному аукциону и основной PostgreSQL.

---

### Этап 6. Постепенно выделять сервисы

После этого можно постепенно выделять:

* сервис рекламного аукциона;
* сервис кампаний;
* сервис статистики;
* сервис финансов;
* сервис аналитики.

---

## 10. Ожидаемый результат

После перехода к целевой архитектуре система должна стать устойчивее и быстрее.

Ожидаемые улучшения:

* рекламный аукцион меньше зависит от PostgreSQL;
* рекламный запрос не зависит от синхронного вызова Auth Service;
* показы и клики не перегружают основную БД;
* отчёты не мешают показу рекламы;
* финансовые данные отделены от статистики;
* авторизация и управление доступами вынесены в отдельный сервис;
* самые нагруженные части можно масштабировать отдельно;
* деплой становится безопаснее.

---

## 11. Итог

Целевая архитектура AdScale должна развиваться постепенно.

Не нужно сразу переписывать всю систему на микросервисы. Но и оставлять текущий монолит без изменений нельзя,
потому что он уже не справляется с требованием по времени ответа.

Лучший вариант — постепенно выносить самые проблемные части из монолита: сначала кэш и события, потом авторизацию,
аукцион, статистику, финансы и аналитику.

Auth Service нужен для пользователей, ролей, JWT и DSP API keys, но он не должен замедлять критический путь рекламного запроса.
