# Task1 — Архитектурное видение AdScale

## Краткое описание

В рамках задачи проведён анализ текущей архитектуры рекламной платформы **AdScale** 
и предложено целевое архитектурное состояние системы через год.

AdScale обрабатывает рекламные запросы от DSP-партнёров, проводит аукцион ставок, отдаёт рекламный ответ пользователям, 
собирает статистику показов и кликов, управляет бюджетами рекламодателей, обрабатывает доступы партнёров 
и предоставляет отчётность через личный кабинет.

Сейчас система реализована как монолит с единой PostgreSQL-базой данных. При пиковой нагрузке около **15 000 RPS** 
система уже не укладывается в требование по времени ответа:

* требование — **P95 ≤ 100 ms**;
* сейчас — **P95 110–120 ms**.

Основные проблемы текущей архитектуры:

* Auction Engine обращается к PostgreSQL во время обработки рекламного запроса;
* показы и клики пишутся напрямую в основную PostgreSQL;
* аналитика строит тяжёлые отчёты по той же базе данных;
* одна PostgreSQL используется почти всеми частями системы;
* авторизация, доступы DSP-партнёров и бизнес-логика находятся внутри общей системы;
* нет кэширования быстрых данных для аукциона;
* нет брокера сообщений;
* разные части системы нельзя масштабировать отдельно;
* деплой выполняется вручную и без контейнеризации.

Для развития системы предлагается подход **Strangler Fig Pattern**. Это значит, что монолит не переписывается 
полностью за один раз. Вместо этого из него постепенно выносятся самые проблемные части.

В первую очередь предлагается:

* убрать PostgreSQL из критического пути рекламного аукциона;
* добавить Redis для быстрых данных аукциона: кампаний, ставок, таргетинга и бюджетов;
* добавить Gateway как единую точку входа для внешних запросов;
* выделить Auth Service для пользователей, ролей, JWT, refresh tokens и DSP credentials;
* проверять DSP-партнёров на Gateway по быстрой read-модели credentials;
* отправлять события показов, кликов, ставок, кампаний, бюджетов и доступов в Kafka;
* отделить аналитику от основной PostgreSQL и использовать ClickHouse для отчётов;
* постепенно выделить сервис рекламного аукциона, сервис кампаний, сервис статистики, сервис финансов, 
сервис аналитики и сервис авторизации.

Целевые backend-сервисы предлагается реализовывать в едином стеке на **Go**. Это упрощает разработку, поддержку, 
CI/CD и эксплуатацию. Инфраструктурные компоненты остаются отдельными технологиями: 
PostgreSQL, Redis, Kafka, ClickHouse и API Gateway.
